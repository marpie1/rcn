SODOTO Issuer — Guide

How to issue a skill credential, and how the three tabs fit together. See One · Do One · Teach One

The SODOTO (See One, Do One, Teach One) Issuer records that a learner has seen, done, and taught a skill, then issues them a cryptographically signed badge. The badge lives on the learner's FedWiki portfolio page and verifies in any browser with no server call — the signature is checked locally against the issuer's public identity. The issuer's private key never leaves your browser.

The workflow

Left to right: the three tabs, in the order you use them.

  1. Register the people in the Registry — the learner, and anyone who will mentor a gate. Each person carries a decentralized identity (DID) that badges bind to.
  2. Define the contract in the Contract tab — one issuer, one skill, one learner. This names what is being credentialed and to whom.
  3. Record each gate — See One, then Do One, then Teach One — as the learner completes them, with the mentor and the outcome for each attempt.
  4. Sign & issue the badge in the Sign & Issue tab once the gates are complete.
  5. The signed badge is written to the learner's portfolio and recorded in the ledger. Anyone can open it and click Verify.

Registry — who can be credentialed

The Registry is the roster of people the tool knows about. Everyone who appears as a learner, mentor, or student elsewhere in the tool comes from here.

What each person carries

  • Name — links to that person's portfolio page on the wiki.
  • DID (did:key:z6Mk…) — their decentralized identity. A badge is issued to this DID, so a verifier can confirm it belongs to the right person, not just to a name anyone could type.
  • Site — the FedWiki host that holds their pages. Each person has their own (their-slug.wiki-sodoto…); only the demo cast shares the base site. Links elsewhere in the tool are built from this, so a wrong site here means links that point at pages which do not exist.
  • Portfolio slug — the page on that site where their badges and history live.
  • Own site — either ✓ own site, or a Provision button.

Needs attention, All, and search

The tab opens on Needs attention: only the people who need something done, with a count on the button. Each one carries a tag saying why, and the buttons under the search box narrow the list to one reason. Red tags block issuing and are listed first:

  • shared DID — another entry has the same DID. It is almost always one person registered twice; keep the right entry and remove the other.
  • bad DID — not a complete did:key, usually cut off when it was copied.
  • no portfolio — no portfolio page, so a badge has nowhere to go.

The yellow no own site tag means the person is still on the shared site; Provision fixes it. The demo cast stays on the shared site on purpose and is never flagged.

All shows everyone. In either view the search box matches name, slug, site, or any part of the DID, and the table shows 50 people a page. When you add someone, the table switches to show just their new row, so you can check it; clear the search to go back.

How to use it

Add a person by entering their name (the slug and portfolio slug fill in automatically) and their DID, then Add to registry. The learner, mentor and student boxes on the Contract tab search this list: type part of a name and pick from the matches. Each match shows the person's site and the end of their DID, so two people with the same name can be told apart. On the pilot, the demo people (all prefixed DEMO —) are seeded here for you.

One person, one DID

A DID can be registered only once. If you paste a DID that already belongs to someone, the tool refuses and names who holds it — that is almost always the same person arriving twice, and you should use their existing entry. If they have lost their key, do not register a new DID for them yet: ask them to restore from their recovery file first. A ⚠ in the DID column marks entries from before this rule that share a DID with another entry.

Onboarding someone new

Do not ask anyone for a private key, and do not make one on their behalf. Enter their name, click Make onboarding link, and send them the link. They mint a key in their own browser, save a recovery file, and send back only their public DID — which is safe to share. Paste it in and Add to registry.

Provisioning their site

Provision gives that person a site of their own: the site itself, a scaffolded portfolio page carrying the sign-in button, and an owner record bound to their DID so nobody else can claim it. The person moves to their new site only after the server confirms it exists, so a failure leaves them exactly where they were.

This happens by itself when you click Add to registry. The Provision button is only for people it didn't reach: someone added while the server was down, a failed attempt, or people registered before this was automatic. Provision them before you record any gates. A gate recorded first is written to the shared site, which the person can't sign in to, and Provision does not move it. The Contract tab warns you if the learner you pick has no site yet.

A restart is needed before they can sign in. FedWiki reads its list of sites, and each site's owner record, only when it starts. Tell whoever runs the server after you provision — or after anything changes a person's DID — otherwise sign-in fails with "this portfolio belongs to a different identity" even though the file on disk is correct.

Contract — what is being credentialed

A contract is the unit of credentialing: one issuer, one skill, one learner. Choosing those three sets up the record that the gates attach to.

The three gates

SODOTO credentials a skill through three gates, recorded in order:

  • See One — the learner observed the skill performed.
  • Do One — the learner performed it, assessed by a mentor.
  • Teach One — the learner taught it to someone else.

Recording a gate

For each gate you record the mentor, the date, what the mentor and learner each assert, the outcome, and a narrative slug (a wiki page for the story of that gate). A gate can take more than one attempt — each attempt is recorded. Recording a gate writes an entry to the learner's portfolio and, for the mentor, a row in their Mentoring Log.

Sign & Issue — make it a credential

Once the gates are complete, this tab turns the contract into a signed badge.

How signing works

You review the credential, then paste the issuer's private key seed (a 64-character hex string). The badge is signed in your browser using that key — the key is never sent anywhere. The result is a signed JWT (JSON Web Token) embedded in the badge.

Where the badge goes

Signing writes the badge to the learner's portfolio page and adds a row to the rcn-sodoto-ledger. On the portfolio, the badge renders with its seal, gate dates, and a Verify button that checks the signature locally — proving the badge is genuine and unaltered, with no call back to any server.

The pilot uses a demo cast. For testing, select the DEMO Academy issuer and the DEMO — learners, and paste the DEMO Academy seed. Nothing signed with real institutional keys should go on the pilot until it's secured — the demo prefix keeps demo badges from ever being confused with real ones.
