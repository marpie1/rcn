Stock & Flow Modeling — The Stella Approach

How STELLA/iThink represents stocks, flows, and valves — and how it maps to an implementation strategy

Element Dictionary
Complete Example — Simple Population Model
The Stella approach, spelled out: The valve (the ✕ circle) is stored as a regular node in the nodes array — it just has a special type:'valve' field and renders differently. The pipe segments on either side are stored as two regular edges with a special type:'flow' style — drawn thick with no arrowheads except the final one. This means connectors can point at the valve node exactly the same way they point at any other node. No new architecture needed.

How Stella elements map to this tool's data model

Stock

  • A node with type:'stock'
  • Shape: rect, thick border (e.g. 3px), light blue fill
  • Extra fields: initialValue, equation
  • Displayed name + initial value below

Valve (Flow node)

  • A node with type:'valve'
  • Renders as circle with ✕ through it
  • Extra field: equation (the rate formula)
  • Can receive connectors like any node
  • Placed by user on the canvas; pipe edges auto-attach

Flow (pipe edges)

  • Two edges with type:'flow'
  • Rendered as thick stroked lines (no box, no label)
  • Source edge: Cloud/Stock → Valve
  • Target edge: Valve → Cloud/Stock
  • Arrow only on final segment

Auxiliary & Cloud

  • Auxiliary: node with type:'aux', renders as circle, has equation
  • Cloud: node with type:'cloud', renders as bumpy cloud shape, no label, no equation — just a boundary marker
  • Connectors are existing edges, thin, curved, purple-ish
Why this fits the existing codebase: nodes[], edges[], and renderNode()/renderEdge() already handle type-based dispatch — OPM and NRM already do this. Adding type:'stock', 'valve', 'aux', 'cloud', and 'flow' slots into the same pattern. The equation field is just another node property. The pipe rendering is a new edge draw style alongside curved/dashed/etc.
