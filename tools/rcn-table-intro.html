A graph of four hundred things is a hairball. No layout algorithm rescues it, and no amount of zooming makes it readable. But you rarely want to see everything at once — you want to find one thing among many, and then see what it touches. The table is how you find it. The graph is what happens next.

Why a table, when we have a graph tool

The 2017 Whatcom survey holds 189 organisations, 127 programmes, 46 themes and 28 people — 409 things joined by 770 links. Drawn all at once it is a picture of nothing. Scanned as a list it is immediately useful: you sort by category, you filter for "food", you notice that one foundation appears beside thirty-two other rows.

Tables and graphs answer different questions. A table answers which one? A graph answers what is this connected to? Asking the second question before you have answered the first is what produces the hairball.

The loop

The three tools above are one motion, and it is worth naming because it is the whole point of the table existing:

Scan
Open the table on 189 organisations. Sort by whatever you care about. Hide the columns that are mostly empty. Type a word to filter.
Select
Click a row. The inspector on the right shows everything known about it. Cmd-click a second row and the inspector becomes a comparison instead.
Follow
Press Neighbourhood ↗. The graph tool opens with that row at the centre and everything it is connected to ringed around it.
Grow
Select any node in that picture and press Expand. One more hop arrives, attached to what is already there. Collapse takes it back off.

You never draw the whole graph. You arrive at a small, specific picture by having asked for it.

The comparison inspector

Select one row and the panel on the right describes it: every attribute, every value. Select several and it does something more useful — it keeps the same rows and shows you the values where they agree, marking the rest as differing.

Two neighbourhood associations selected. The inspector shows sources: ENTITY, PERSON and sector: Civil Society as shared, and marks Name and website as differing. Thirty-four columns collapse to the four that carry the answer. A panel built to describe one thing answers what do these have in common? for nothing extra.

Columns where everything agrees on being empty are hidden, because agreed-emptiness tells you nothing.

Inside a wiki page

A table of 189 rows by 34 columns will never fit a wiki column, and shrinking it produces something unreadable that still does not fit. So the page does not show the table — it shows the shape of it.

The dimensions

A page item reads 189×6 with its title, the column names as small chips, and the first few rows as links.

Called out to full width

Open Table ↗ opens the whole thing in its own window, still tied to the page that opened it.

Clicking a name opens its page

Row names are ordinary wiki links. Clicking one opens that subject beside the table — a page if it exists, an invitation to write one if it does not.

Hovering a column drives the charts

Charts on the same page respond to whichever column you point at, with no wiring between them.

What makes it different

  • Original
    Your trail is an address. Every step — the table, the row you opened, the thing you followed it to — is in the page URL. You can paste it to someone and they arrive where you are. Most analysis tools cannot hand anyone their own screen.
  • Rare
    Views agree without being wired together. A table row, a node in a drawing and a name typed in a paragraph all point at the same page, so they stay in step because they name the same thing — not because a programmer connected them.
  • Rare
    The comparison inspector. Selecting several rows turns a description into a comparison, without a separate compare mode to learn.
  • Original
    Ragged data is shown honestly. Real records are patchy. Every column carries how full it is, and thinly-filled ones start hidden rather than being dropped or faked.
  • Rare
    It reads, it does not overwrite. Sort, filter, select, follow. Editing your records is a different job with different risks, kept deliberately somewhere else.

How it compares

A spreadsheetBetter at editing, blind to connection

A spreadsheet is the right tool for typing numbers into a grid. It cannot tell you that this row and that row are the same organisation seen twice, and it has no idea what any row is connected to. The RCN Table is the reading half of a spreadsheet joined to a picture of relationships.

A database query toolDifferent audience

Query tools assume you can write the query. Here the questions are already written and appear as named actions — you press Neighbourhood, you do not compose a traversal. Nobody needs to learn a query language to use their own records.

Business intelligence dashboardsDesigned by someone else

A dashboard is arranged in advance by whoever built it, and every viewer gets the same panels forever. Here the arrangement is made by the person reading, one click at a time, and it differs for every question. Nobody has to anticipate what you will want to see.

Tom Sawyer PerspectivesThe reference we are recreating

Perspectives is the mature commercial version of this idea, and several behaviours here are taken from it deliberately — the comparison inspector above all. The difference is that its views are wired together inside one program, so a selection cannot leave the screen it is on. Ours are joined by public names, so any step can be sent to another person, forked, or written down as a page.

Where it sits

The Graph Tool draws cause. The Map draws place. The Timeline draws time. The Table is how you get to any of them when there are more things than you can hold in your head — the front door to a body of records, and the place a question starts.

It reads from the same store as everything else in the toolset, so a row here and a node in a drawing are the same thing, named the same way.
