RCN Tool Stack

A map of the tools, infrastructure, and data stores that make up the RCN digital commons — how they connect, what each does, and where to read more.

The Full Picture

The RCN tools are not independent applications — they share identity infrastructure, a graph database, a wiki, and a common set of people with cryptographic identities. The diagram below shows all major components and the relationships between them.

Shared Infrastructure

One DID per person, used everywhere

Each person in the RCN has a single did:key identity — a public-private Ed25519 key pair. The same DID appears in their SODOTO credentials (as learner or mentor), in CfA-dSC contracts (as customer or performer), and in any signed history entries they produce. Identity is not tool-specific.

The DID registry: dids.json and people.json

Both files live in ~/rcn/veramo/ and are git-committed (public keys only — private keys stay in keys.json which is gitignored). Both SODOTO and CfA-dSC read from these files. When a new practitioner joins, they are added here once and available to all tools.

Verification is always in-browser

Whether verifying a SODOTO credential badge or (eventually) a CfA-dSC signed history entry, the verification logic uses the same pattern: extract the public key from the did:key string, call crypto.subtle.verify(), report pass or fail. No server. The cryptographic guarantee is the same across both systems.

How the Tools Connect in Practice

A concrete example: a Community Health Worker (CHW) in the Superior AZ NDC.

  1. The CHW earns an eVSM Site Manager credential through SODOTO — three gates, witnessed by a mentor, signed by the NDC. This credential lives in their FedWiki portfolio.
  2. The NDC contracts with a neighborhood association for the CHW to run an eVSM assessment. The contract is a CfA-dSC — negotiated, signed by both parties, payment in fiat plus time-dollars. The CHW's eVSM Site Manager credential is referenced as their qualification.
  3. The assessment runs. The CHW facilitates. The neighborhood association declares satisfaction. The settlement is recorded — a signed document showing the three-currency breakdown.
  4. At TeachOne in the CHW's credentialing path, a student learns from them. When TeachOne passes, a gift relationship is recorded in Neo4j — the student's debt to the CHW for their learning, expressible later as time-dollars in a future CfA-dSC.

Each step uses a different tool. Each tool reads the same identity infrastructure. The FedWiki connects the practitioner's story across all of them.

eVSM is architecturally separate from SODOTO and CfA-dSC — it does not use Veramo, Neo4j, or the DID registry. It produces FedWiki-compatible output but is not currently integrated with the shared identity layer. This may change if eVSM facilitator credentials become part of SODOTO.
