RCN/Design note/14 August 2026

The RCN Toolshelf

A storefront for RCN Tools and Methods, and a rational file layout for the repo behind it — which turn out to be the same piece of work.

The argument

Two questions, one artifact

A storefront needs to know what tools exist, what each is for, and how to launch it. A rational file layout needs exactly the same list. Build that list once, as a file, and both problems are downstream of it.

Today that knowledge lives in an 848-line README.md that only Claude reads, and in a set of memory files that nobody else can see. Neither is a storefront, and neither survives being handed to Kerry or Chris or a new NDC.

The proposal is one machine-readable file — tools/catalog.json — that is the source of truth. Everything else renders from it: the FedWiki site, a standalone dashboard page, and the tool section of the README. One source, several targets, no hand-syncing.

What an entry holds

{
  "id": "graph-tool",
  "name": "RCN Graph Tool",
  "what": "Draw a system as nodes and edges, then argue about it together.",
  "shelf": "see-how-a-system-works",
  "status": "live",              // live | draft | dormant
  "launch": "graph-tool-v22.html",
  "intro":  "graph-tool-intro.html",
  "manual": "graph-tool-manual.html",
  "example": "examples/whatcom-homelessness-cld.json",
  "deck": "decks/rcn-graph-tool-intro.pptx"
}

Eight fields. Filling them in for every tool is the whole first pass, and it is the pass that forces the alive-or-dead call on every file in tools/.

Note what is not in that entry: any mention of which methods the tool belongs to. That absence is deliberate, and the reason is the most important structural decision in this plan. It is set out under Methods are first-class.

Part one

The storefront

The dashboard is the easy half. The missing intros are the work.

There are roughly thirty launchable tools. Six have the full intro-and-manual triad: Conversation Navigator, Graph Composer, Issue Polygon Map, Positive Affect Score, Timeline, Schema Sunburst. The rest are missing one or both — the Graph Tool included, and it is arguably the flagship.

A storefront with twenty-four unexplained doors is worse than no storefront, because it advertises the gap. So the order matters: catalog first, dashboard second, then work steadily down the list writing intros. The dashboard makes the gap visible, which is useful pressure rather than embarrassment.

What makes it a store and not a link list

A tool that opens blank teaches nothing. The examples already exist and are simply unfindable — whatcom-homelessness-cld.json, wardley-bicycle-production.rcn.json, six pomr-*.json files, education-human-becoming-cld.json. Nobody outside this repo knows they are there. The Cave Drawings principle says the first click should land on a filled-in picture that a group can point at and disagree with, not an empty canvas with a toolbar.

Organize the shelf by the question, not the tool type

Categories like “diagramming tools” and “mapping tools” only help people who already know the toolkit. Someone arriving with a problem does not know they need a causal loop diagram; they know their neighborhood keeps having the same argument. The shelves below are phrased as the question the visitor actually has.

FedWiki is the primary storefront decided

The catalog renders two targets, and both exist either way. Calling FedWiki primary settles three specific things.

It is the address people are given. The wiki URL is what goes in decks, in email, on the map, on a card. The standalone file is what you hand to someone with no connection.

New writing lands there. Someone who wants to add “here is how we used the Graph Tool in Superior” writes it on the wiki page, and it stays on the wiki page. The standalone index.html stays deliberately thin — name, one line, launch link, status. A snapshot, not a mirror.

Forking is the intended path, not a curiosity. Only the FedWiki version can be forked by an NDC, who keeps the six tools they actually use, annotates each with their own local example, and stays linked back to the original. That is a storefront that behaves like a network instead of a catalog, and no other hosting arrangement gives you it. Nobody forks a mirror, which is why this only pays off if FedWiki is the one people are pointed at.

The cost is real and worth naming: this arrangement needs the wiki up, and needs a person tending pages. The standalone needs neither and never rots. That is the trade you are making, and it is the same one already settled for the map — the two-file wiki version is the live site, the standalone build is explicitly a handout and explicitly not the live site.

Hosting stays Wiki Café, alongside the Conversation Navigator. Firebase remains database-only.

Generated pages versus living pages

Generated pages get overwritten; FedWiki pages are supposed to be alive and hand-edited. The line to draw: a small number of generated roster pages — the tool shelf and the method index, regenerated whenever the catalog changes — and N hand-owned pages that begin as generated stubs and thereafter belong to whoever tends them. The catalog stays authoritative only for name, launch URL, and status.

Deployment shape

The same dual-target model already settled for the map: tools/index.html reads catalog.js as a flat sibling so it works from file://, and the same catalog generates the FedWiki importer bundle through the existing md-to-fedwiki-page.js. Live site and handout, one source.

Part one, continued

Methods are first-class

A hammer is used in a lot of processes. So a tool cannot carry the sequence — it sits in a different position, doing a different job, in every method that uses it.

This is the correction to my first draft, and it matters more than anything else in the plan. I had put a methods field on each tool. That is wrong twice over: it implies a tool belongs to a fixed set of processes, and it has nowhere to record what the tool is doing there or what it hands to whatever comes next.

The Graph Tool in a trace is drawing an incident — who did what, what followed what. The Graph Tool in a Vester run is drawing an influence matrix. Same tool, same file, entirely different job, different output, different next step. One field on the tool cannot hold that.

So sequence lives on the method. Tools and methods are many-to-many, and the join carries information of its own.

tools/methods.json

{
  "id": "trace-then-timeline",
  "name": "Trace, then Timeline",
  "confidence": null,     // DERIVED from SODOTO attestations — never typed
  "retired": null,        // or { when, why } — kept visible, not deleted
  "problem": "People remember the same events in different orders,
              and the argument never resolves.",
  "context": "After an incident, or a stretch of history people
              recall differently.",
  "completes": ["neighborhood-incident-review"],   // larger methods
  "steps": [
    {
      "tool": "graph-tool",
      "does": "Draw the trace — who acted, what followed what.",
      "produces": "Graph JSON, nodes carrying dates",
      "handoff": "Export Wiki JSON. Dated nodes become timeline events."
    },
    {
      "tool": "rcn-timeline",
      "does": "Lay the traced events out in time and test the order.",
      "produces": "Intervals with Allen relations",
      "handoff": null  // terminal step
    }
  ]
}

The load-bearing field is does. It is where the hammer problem gets solved — the same tool gets a different sentence in every method, written from inside that process rather than from the tool's own point of view.

handoff is the second one. It is the thing that is never written down anywhere today, and it is the thing that actually stops people: they finish in one tool and do not know what to carry across, or in what shape.

A tool page's “used in these methods” list is derived — generated by scanning methods.json, never typed by hand. Hand-maintained back-links drift the moment a method changes, and this way they cannot.

The methods we already have, scattered

  • Trace → Timeline — buried in the README as a paragraph.
  • Rent Band Analysis — a loose markdown file in the repo root.
  • The Vester run — module mapping worked out, spread across vester/ and notes.
  • SODOTO issuance — the issuer guide is the closest thing to a method page that exists, and it is a good model for the format.
  • The eVSM survey cycle — four HTML files that are stages of one process, currently presenting as four unrelated tools.

You have a good deal of work on sequencing tool use already, arriving separately. That material should feed methods.json directly rather than being reinvented from the tool side — which is the strongest argument for writing the method pages before the tool intros.

The structure

A method is a pattern

Alexander is already the first name in this project's intellectual stack, and the structure of A Pattern Language turns out to describe what we just designed — closely enough that it is worth taking the rest of it rather than rediscovering it piecemeal.

One correction to the mapping first. It is tempting to read tool as pattern. That is wrong. Alexander's patterns are not instruments; they are claims about what works, each with a context, a problem, evidence, and a solution. Our methods are the patterns. Our tools are the materials a pattern calls for.

The consequence is that Alexander's page format becomes the method-page template, already tested across 253 of them.

The confidence marker is earned, not declared

Alexander marks each pattern with two asterisks, one, or none — how sure he is that it is a true invariant rather than one good way among many. He is candid about the weak ones, and the book is more trustworthy for it.

Methods carry the same mark. But a mark you type is a mark you can inflate, and within a year of generous self-assessment the field becomes decoration. So it is not typed. It is derived from SODOTO attestations — which is what SODOTO has been for all along: learning how to learn, and sharpening or discarding tools and methods as we find out.

MarkWhat it claimsThe evidence that earns it
∗∗A real invariant — it survives being handed onA Teach One whose learner then ran it themselves, ideally in a second NDC
∗∗It worked, at least once, for someoneAt least one Do One
∗∗Reasoned out, never run with a groupNo attestations. The normal, publishable starting state
RetiredTried, and it did not holdKept on the shelf with the date and the reason

Because a star is computed from signed credentials, it cannot be talked up. And zero stars is not a failure state — most of what gets written first will honestly sit there, and saying so is the whole point.

Teach One tests the method, not the person

This is the load-bearing part. A method that only its author can run is not a method — it is a skill, with half of it living unwritten in one person's head. Alexander's criterion for a pattern is exactly that someone else can pick it up and reuse it, and Teach One is the moment you find out whether that is true.

The credential says a person learned something. The aggregate across credentials says the method survived transmission. Same signatures, two different readings, and the second one is new.

Alexander's markers froze; ours move

A Pattern Language is a book, so its confidence marks were fixed at publication in 1977. He had to guess once and commit to print. Ours move — up as a method gets taught and the teaching takes, down or stale as it goes unused. A two-star method whose last attestation was three years ago is telling you something no book can say.

That is the sharpening half. Retired is the discarding half, and it stays visible on purpose: a method someone tried and abandoned is not the same as one nobody ever touched, and both would otherwise read as zero. Keeping the failure with its reason is how a group stops repeating it. Deleting it throws away the most expensive thing anyone learned.

The risk that would kill this

If recording “we ran Trace → Timeline with the Superior group” costs ten minutes of credential ceremony, nobody records it, every method sits at zero forever, and the shelf looks admirably honest while actually being empty of data. Untested and unlogged must never resolve to the same mark. The attestation for a method-run needs to be near-free — closer to the existing sign-your-gate flow than to issuing a credential — and the interface should distinguish “no evidence” from “evidence of nothing happening.”

Kept separate from tool status

A tool's live-or-draft state and a method's confidence are different facts. A shipped, polished tool can sit inside a method nobody has ever run. Conflating them would let good software vouch for an untested process, which is precisely the error the marker exists to prevent.

Two edge types, not one

Alexander's links are scale containment — Mosaic of Subcultures contains Community of 7000. Ours are mostly sequence with a handoff — trace, then timeline. Those are genuinely different relations and should not be flattened into “related to.”

But we need both, because some of our work does nest: the eVSM cycle contains four stages, and SCP contains nineteen plugins. So:

  • HANDS_OFF_TO — step to step, within a method. Carries the handoff description. Directed, ordered.
  • COMPLETED_BY — method to smaller method. Alexander's downward link. Directed, unordered.

Two typed relations plus USES from a step to a tool. Three edge types is about the right vocabulary size for something a group has to read.

Never draw the whole graph

The single most useful thing Alexander does structurally: with 253 patterns, he never once shows the full graph. Each pattern page shows only its immediate links up and down, and the front matter carries a handful of short example languages — a porch, a cottage — as ordered lists of pattern numbers.

That is the interface specification for the storefront, and it arrives free. Thirty tools crossed with a dozen methods is already past what anyone can read as one picture. Show the selected path, never the atlas. A method page shows its own steps and its immediate neighbours; the shelf shows short example sequences. Nothing renders the whole network, ever.

And the deepest borrowing, which is the thing you have had in mind for years: a language is a selected, ordered subgraph, and selecting it is the design work. A method is not a description of how the tools happen to connect. It is a choice somebody made for a particular job — which is precisely why it cannot live on the tool.

The substrate

What Neo4j buys, and when

Worth separating two claims, because they come true at different times: Neo4j helps us as soon as the methods exist, and helps users only through a lens we build on top of it.

For us, immediately

  • The derived back-link. “What methods use this tool” stops being a script and becomes one hop.
  • Impact analysis before a rename. “If the Bias Checker becomes the Conversation Navigator, what breaks?” — asked and answered before the rename, not after.
  • Gap-finding. Tools that appear in no method are either undocumented or genuinely unused, and the query cannot tell you which — but it can hand you the list to decide.
  • The confidence marker itself. For a given method, count attestations by type and by NDC: any Do One earns a star, a Teach One whose learner then ran it earns the second. This is the query that makes the mark underivable by hand and therefore trustworthy — and it runs against the SODOTO projector already on the roadmap.
  • Staleness. Most recent attestation per method. A method nobody has run in two years is telling you something, and only a live graph can say it.

For users, once there is a lens

One query justifies the whole substrate: what routes exist from what I have to what I need. Someone with a graph JSON who wants a published FedWiki page is asking for a shortest path over HANDS_OFF_TO edges. That is Alexander's “make a language for your project”, executed as a traversal, and it is the first thing in this plan that reaches past us to a person in a neighbourhood.

Two cautions, both mild. Nobody will write Cypher — the value reaches users strictly through a page that runs the query for them, which is consistent with the substrate direction already set, where tools become lenses. And the graph does not exist yet, which is the hard part. Writing a dozen honest methods is months of thinking; loading them into Neo4j is an afternoon.

The files stay the source

catalog.json and methods.json remain the human-editable, git-diffable, file://-readable truth. Neo4j is a projection, rebuilt from them — the same arrangement as the SODOTO projector. If the database is down, the storefront still works and the handout still opens. Nothing load-bearing sits only in the graph.

Part two

Organizing the files

You asked what confuses me. Specifically, this:

01

No alive-or-dead marker anywhere

checklist-test.html, sodoto-crypto-test.html, conversation_index (old).html, evsm-svg-v3.html, session-builder (1).html. I cannot distinguish an experiment from a shipped tool without opening it. This is the single largest source of confusion — larger than the directory layout.

02

tools/ mixes four different kinds of thing across 157 files

Launchable tools, their documentation, example data, and utility scripts (unwrap-md.js, validate-rcn-graph.js, brain-to-graph.py, split-wa-health-aspects.py) all sit side by side. Nothing in a filename tells me which kind I am looking at.

03

Stem mismatches break any convention I infer

graph-tool-v22.html but graph-tool-intro.html. And the Bias Checker's files are named bias-checker-* while every page inside them is titled “Conversation Navigator” — the tool was renamed and the filenames were not.

04

Underscores and hyphens are mixed

eip_integration_explorer.html next to issue-polygon-map.html. Guessing a filename fails about half the time.

05

Fifteen loose files in the repo root

Two Python proxies, a .tar.gz, a .brz brain export, a stray graph JSON, a stray HTML page, and several markdown documents with no home.

06

archive/ is empty, but the README says it holds old drafts

A small thing that costs a lot: once one README claim is stale, I trust the rest of it less everywhere.

07

Vendored directories dominate every search

vester/ holds 2,245 files, groove-workspace/ 1,131, wiki-plugin-rcn-outliner/ 216 — mostly node_modules. Any repo-wide search hits dependencies before it reaches your work.

What I would not do: a big-bang reorganization

Several tools load their siblings by flat filename because file:// offers no alternative. The Graph Composer reads families.js and graph-sets.js from its own folder; the map loads rcn_static_data.js the same way. Moving those breaks things silently, and no test suite can catch a broken file:// page. The blast radius is invisible, which is the worst kind.

So the moves below are ordered by value per unit of risk, and each one carries its actual risk.

Then shrink the README to pointers

It is doing catalog work today, which is why it is 848 lines and why it goes stale. Once the catalog exists, the README describes the shape of the repo and points at the catalog — and stops trying to be one.

Build order

Where to start

This part genuinely is a sequence — each step depends on the one before it.

Draft the catalog schema and populate it for all thirty tools

One pass, nine fields each. It forces the alive-or-dead call on every file, gives the dashboard its data, gives the FedWiki site its pages, and gives Claude the map it is currently missing. Everything else is downstream.

Write two method pages as prose, before any schema

Trace → Timeline and Rent Band Analysis. Prose first and deliberately — you cannot design the methods schema until you have written two real methods and seen what they needed to say. Both were chosen because their tools are already documented, so neither page has a dead link. Fold in your existing sequencing work here.

Derive methods.json from those two pages

The schema falls out of the writing rather than the writing being forced into a schema. If the does and handoff fields turn out to be the wrong shape, this is the cheap moment to find out — two pages in, not twenty.

Build tools/index.html against both files

Flat-sibling catalog.js so it runs from file://. Shelves by question, cards with four actions, and derived “used in” links from the methods. A day, not a week, because the data already exists by then.

Make the safe moves

examples/, decks/, root cleanup, empty archive/ filled. Update the four manual links that name example files.

Publish to Wiki Café — this is the go-live

Generate the shelf page, the method index, and the tool stubs through the existing converter, and push. From this moment the wiki is the address you hand out, the pages are hand-owned, and the two roster pages are regenerated from the catalog.

Write the missing tool intros, shaped by what the methods asked for

Roughly twenty-four. By now you know what an intro has to answer, because two method pages have already demanded it — what this tool takes in, what it hands off, and in what shape. The Graph Tool's intro exists but its file stems disagree; MORE Outliner has a manual and no intro; the eVSM stages need one intro for the whole cycle rather than four.

Add the remaining methods

The Vester run, SODOTO issuance, the eVSM survey cycle, and whatever else your sequencing work turns up. Each one is cheap by this point: the format is proven, the schema is stable, and the tools it names are documented.

Settled

Decisions of record

FedWiki is the primary storefront decided

The wiki site on Wiki Café is the address people are given; the standalone index.html is a thin file:// handout, not a mirror.

What follows: forking is designed for, not tolerated. New writing about a tool belongs on its wiki page. The standalone deliberately carries less, and that is not a defect to be fixed later.

Methods come early, and are first-class decided

Two method pages get written before the bulk of the tool intros, and methods live in their own file with their own ordered steps.

What follows: the tool entry has no methods field. Sequence and the per-step job description live on the method, because a tool does a different job in each process it appears in. Back-links on tool pages are derived, never typed.

Method pages follow Alexander's pattern format decided

Context, bold problem statement, body, solution, diagram, links down — plus a confidence marker on every method.

What follows: three typed edges (USES, HANDS_OFF_TO, COMPLETED_BY), and a hard interface rule — show the selected path, never the whole graph.

Confidence is derived from SODOTO, never typed decided

A method's stars are computed from attestations: a Do One earns the first, a Teach One that takes earns the second. Zero stars is a normal, publishable state.

What follows: confidence is a computed field, not an authored one. Retired methods stay on the shelf with their reason. And the method-run attestation has to be near-free, or untested and unlogged collapse into the same mark and the whole signal dies.
