NixOS for RCN
What we would actually gain — and what we would actually pay — if the whole RCN stack, Federated Wiki included, were deployed as NixOS.
August 14, 2026 · exploratory note · no decision attached

Status: exploration, not a proposal

Nothing in this note is decided, scheduled, budgeted, or recommended for adoption. It exists to answer a question that came up in conversation — "what would we get out of it?" — with enough specificity that the answer is worth something later. Treat every "we could" as a sketch, not a plan. The current deployment model (three GHCR containers behind Caddy on WikiCafe) is unchanged and unchallenged by this document.

The short version: we have already been drawing Nix by hand. The SODOTO dependency closures in docs/assets/sodoto-dependency-closures.json assert what each deployment artifact contains. Nix computes that same relationship instead of asserting it, and can sign the result. Whether that is worth the cost depends almost entirely on how many NDC servers we expect to be running, and how much we want the FedWiki plugin loop to stay fast and live.

What the question is really about

RCN's unit of deployment is not a container. It is a neighborhood site: a wiki, the sofi-proxy, Caddy terminating HTTPS, seed data, an identity key, and a backup story, all standing up together and staying consistent with each other. Docker Compose describes the containers well. It does not describe the machine.

NixOS describes the machine — kernel, services, users, network, disks, and the applications — as a single declarative expression that evaluates to a bootable system. That is the whole of the appeal here, and every specific benefit below is a consequence of it.

What we would gain

An NDC server becomes a readable text file

One configuration per neighborhood, diffable, storable in FedWiki itself, and legible to someone who is not the person who built it. This is the cave-drawings principle applied to infrastructure: an artifact a group can read, point at, and argue about without special training. Today, "what is actually running at this site" is answerable only by someone with a shell on the box.

Rollback that a non-expert can perform

NixOS keeps previous system generations and lists them in the boot menu. If an upgrade breaks the wiki at an NDC on a weekday evening, someone on site reboots and picks the previous generation — OS, service versions, config, and data layout all reverting together as one atomic unit. Nothing in the current stack offers that as a single step.

Offline and low-bandwidth installation

A closure can be copied to a USB stick and carried to a site with poor connectivity, arriving bit-identical to what runs on WikiCafe. For rural NDCs this is a practical capability, not a convenience.

The provenance shape matches the identity story

This is the most interesting alignment, and the least obvious. RCN's thesis is signed substrate — did:key identities, badge JWTs, self-custody, verification without a registry and without a chain. A Nix closure is a content hash, and store paths can be signed and verified by anyone holding the public key.

"This NDC runs exactly closure X, signed by the RCN key" is structurally the same claim as a badge: independently verifiable, no central registry, no trust required in the host. Machines would get the same treatment people already get. That is a coherent extension of the signed-substrate position rather than an unrelated devops upgrade.

The dependency diagrams stop being hand-maintained

The closures document asserts that the deploy artifact contains sofi-proxy plus the tools plus the seed. Nix computes that relationship, and nix why-depends answers it on demand. Hand-drawn diagrams drift from reality; computed ones cannot.

Development shells without polluting the laptop

A pinned Node for FedWiki plugin work, a pinned Python for the FHIR smart-proxy, a Neo4j for substrate work — each entered per-project and each leaving nothing behind.

What it would cost

Federated Wiki fights immutability — this is the real objection

Plugins install through npm into the wiki's own directory. Pages are written to disk as the primary act of using the system. Farm mode creates sites at runtime. The entire value of a wiki is mutable state that responds immediately to a person.

Under Nix, application code lives in a read-only store, and every plugin becomes a derivation with a pinned hash. Adding a plugin stops being an install and becomes a configuration edit plus a system rebuild. With sixty-four plugin repositories and active work aimed at making the wiki more live rather than less, this is a genuine cost in the direction we are trying to move.

The forced separation it imposes — application code in the store, all mutable data in explicitly declared persistent paths — is a discipline worth having regardless. The slower plugin loop is not.

Concentrated expertise

Nix's error messages are notoriously poor and its learning curve is steep. A neighborhood volunteer can read a Compose file and guess right. They cannot read a flake. Anything that pushes debugging back to one person works against the coordinatorless direction.

Uneven payoff across the stack

The single-file browser tools have no build step at all and gain nothing. Firebase is a hosted service and is unaffected. Neo4j Enterprise packaging is a project in its own right, separate from anything else here.

If it were ever pursued, the staged shape

The payoff is uneven enough that an all-at-once move would take the costs and the benefits together when they can be separated. A staged approach takes them in order of return.

1

Use Nix to build the containers, not to run them

Produce the same three GHCR images reproducibly, with no Dockerfile drift and a computed dependency closure. WikiCafe changes nothing, the push path is unchanged, and the packaging work needed for anything further gets proved out.

Low risk, contained blast radius, reversible by deleting a directory.

2

NixOS for the NDC host

A single module declaring wiki, proxy, Caddy, backups, and the site's identity key, with one configuration file per neighborhood and all mutable data held in explicitly declared paths outside the store. This is where rollback, offline install, and signed provenance pay for themselves.

Worth considering only once hand-tending individual servers has become the bottleneck — realistically the third or fourth NDC, not the first.

3

Never the plugin development loop

Plugin work stays on npm and symlinks against a local wiki. Nothing about the packaging approach for deployment requires changing how plugins are written and tested.

A boundary to hold deliberately, not a stage to complete.

Open questions

  • How many NDC servers do we actually expect to be running, and over what period? Below roughly three, hand-tending is cheaper than any reproducibility machinery.
  • Does the wiki's mutable state separate cleanly in practice, or are there paths where code and data are genuinely interleaved?
  • Is a signed closure hash something an NDC would ever be asked to present — or is the provenance argument elegant but unused?
  • Who besides one person would be able to debug a failing rebuild at a site?
  • Would this compete for attention with the FedWiki affordances work, which is the thing actually blocking use?

The honest summary

The strongest argument is not operational efficiency. It is that a signed, content-addressed machine closure is the infrastructure analogue of a signed did:key badge — the same trust shape, verifiable by anyone, dependent on no registry. RCN already made that argument for people. Making it for machines is consistent rather than novel.

The strongest argument against is that Federated Wiki is built on exactly the mutability that Nix removes, and the current work is aimed at making the wiki more live, not more sealed.

Stage one — building the existing containers with Nix — captures most of the reproducibility with almost none of the cost, and can be abandoned without consequence. Everything past that should wait for a real operational pain that a real number of NDC servers has produced.
