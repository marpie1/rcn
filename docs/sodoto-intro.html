See One, Do One, Teach One

A federated apprenticeship credentialing system for RCN practitioners. Skills are witnessed, practiced, and taught — then cryptographically certified by a Neighborhood Development Cooperative.

What SODOTO Is

SODOTO issues W3C Verifiable Credentials for practitioner skills. The credential documents not just that you have a skill, but how you acquired it: who showed you, who witnessed your practice, and who you subsequently taught. The full chain of transmission is embedded in the credential and cryptographically signed by the issuing NDC organization.

No central server is required to validate credentials. Anyone viewing a learner's FedWiki portfolio page can click Verify — the browser extracts the issuer's public key directly from the DID string and confirms the signature. No registration, no login, no third-party service.

Credentials are issued by NDC organizations, not individuals. The credentialing authority is the cooperative — persistent, institutional, not dependent on any one person.

The name comes from a medical training tradition: you observe a procedure done by an expert, you perform it yourself under supervision, and you teach it to the next learner. Each step is a gate. All three must pass before a credential is issued.

The Three-Gate Workflow

Every SODOTO credential passes through three sequential gates. Gates cannot be skipped. A gate may require multiple attempts — the record of each attempt, including failed ones, is preserved in the credential's history.

Gate 1

See One

The mentor demonstrates the skill in a real working context. The learner observes closely. Both record a brief assertion — the mentor that they showed the skill, the learner that they understood what they observed. The session is documented in a FedWiki narrative page.

Gate 2

Do One

The learner performs the skill themselves. The mentor witnesses the full session. Both record assertions. If the mentor is not satisfied, the attempt is recorded as ended and another DoOne is scheduled. There is no penalty for multiple attempts — the history is evidence of rigor, not failure.

Gate 3

Teach One

The learner teaches a new student, with the mentor present to witness the teaching. Both the mentor and the student attest. The student's subsequent DoOne page serves as the evidence record — the learner cannot claim TeachOne without a real student who actually did the skill.

Each gate also records the mentor's name and DID, a date, and a link to a FedWiki narrative page. The TeachOne gate adds the student's name, DID, portfolio slug, and the slug of the student's DoOne evidence page.

Issuing a Credential — Coordinator Steps

The coordinator uses sodoto-issuer.html — a browser-based tool that handles gate recording, signing, and all FedWiki writes. No CLI scripts or git commits are required.

  1. Open the issuance tool. Navigate to sodoto-issuer.html on the SODOTO server. The tool loads the people registry automatically.
  2. Confirm the learner is in the registry. Check the Registry tab. If the learner is not listed, add them — enter their name, DID, FedWiki site, and portfolio slug. New entries sync to the server-side registry automatically.
  3. Open the contract. On the Contract tab, select the issuing NDC organization, the skill, and the learner. Click "Open / Resume Contract." The tool tracks gate state per issuer–skill–learner combination.
  4. Record gate attempts. For each gate (SeeOne, DoOne, TeachOne), select the gate tab, fill in the date, mentor, both assertions, outcome, and narrative page slug, then click "Record Attempt & Write to FedWiki." The tool writes HTML items to both the learner's and mentor's portfolio pages immediately.
  5. Sign the credential. Switch to the Sign tab. Review the credential preview. Select "Full credential" once all three gates are complete (or "Partial" to issue mid-process). Enter the issuing NDC's 64-character hex private key seed and click "Sign & Issue." The JWT is signed entirely in the browser using the Web Crypto API — the key is cleared immediately after use and never sent to any server.
  6. Badge is written automatically. The tool posts the signed badge to the learner's FedWiki portfolio via sofi-proxy and updates the RCN SODOTO ledger page. No manual file editing required.
  7. Verify in FedWiki. Open the learner's portfolio page and click the Verify button on the new badge. Confirm it returns ✓ Verified. If it fails, the private key seed used did not match the issuing NDC's DID.
Guard the private key seed. Each NDC's Ed25519 private key seed is a 64-character hex string. It is never stored by the tool — coordinators must keep it in a secure location (macOS Keychain, password manager, or encrypted file). If it is lost, the NDC can no longer sign new credentials under that DID. Existing credentials remain valid permanently — they only need the public key (encoded in the DID string) to verify.

The Learner's FedWiki Portfolio

Each learner has a FedWiki page — for example, marc-pierson-sodoto-portfolio — that displays their credential badges. Pages are written by sofi-proxy directly to the FedWiki filesystem and served through the standard FedWiki server.

Each badge on the portfolio page is rendered by the sodoto-badge plugin and displays:

  • The skill name and the issuing NDC's seal
  • The three gate completion dates
  • Mentor name(s), each linking to their own portfolio page
  • The full attempt history for each gate (including any failed attempts)
  • A Verify button that confirms the credential signature in-browser

The badge plugin reads the credential's JWT from the page markup. The JWT is the credential — if the badge shows and the Verify button passes, the credential is authentic and unmodified.

How Verification Works

The did:key format encodes the issuer's public key directly in the DID string. No server, no registry lookup, no external dependency. Anyone with the DID can recover the public key.

When a user clicks Verify, the sodoto-badge plugin performs these steps entirely in the browser:

  1. Extract the jwt string from the credential markup on the page
  2. Split the JWT into its three parts: header, payload, signature
  3. Decode the payload and read the iss field — this is the issuer's did:key string
  4. Decode the multibase suffix of the DID to recover the raw Ed25519 public key bytes
  5. Call crypto.subtle.verify() with those key bytes, the header.payload string, and the decoded signature
  6. Report ✓ Verified or ✗ Failed

This means credentials are permanently verifiable with no server, no expiry, and no reliance on any third party — as long as the DID string and the JWT are intact. The credential is self-contained.

Neo4j — The Teaching Graph

SODOTO is designed to write its credentialing data into Neo4j so that teaching chains, debt relationships, and credential provenance are queryable as a graph. The schema is fully designed; writes from SODOTO to Neo4j are part of the v0.4 work and not yet implemented. The CfA-dSC system does write to Neo4j today.

Key relationships

// Teaching lineage — queryable to any depth
(mentor:Person)-[:TAUGHT { skill, contractId }]->(learner:Person)

// Mentor attestation per gate
(mentor:Person)-[:ATTESTED_SEE_ONE   { completedAt, contractId }]->(learner:Person)
(mentor:Person)-[:ATTESTED_DO_ONE    { completedAt, contractId }]->(learner:Person)
(mentor:Person)-[:ATTESTED_TEACH_ONE { completedAt, contractId, studentDid }]->(learner:Person)

// Learner acknowledgement back to mentor
(learner:Person)-[:ACKNOWLEDGED_MENTOR { gate, contractId }]->(mentor:Person)

// Credential chain
(learner:Person)-[:HOLDS]->(c:Credential)
(org:Organization)-[:ISSUED]->(c:Credential)
(c:Credential)-[:CERTIFIES]->(skill:Skill)

// Gate attempts as first-class nodes
(person:Person)-[:ASSERTED { value, at }]->(attempt:GateAttempt)
(teachOneAttempt:GateAttempt)-[:EVIDENCED_BY]->(studentDoOne:GateAttempt)

The debt model

Debt is owed to the commons — not to the mentor. When TeachOne completes, a (:Debt) node is created and the relationship is:

(learner:Person)-[:OWES { skill, createdAt, status }]->(commons:Organization {slug: "commons"})

Debt is retired in two stages: DoOne completion retires the first half, TeachOne completion (with student acknowledgement) retires the second. The student's TeachOne creates a new debt — forward propagation, no cycles. Each TeachOne is real value creation: a new competent practitioner in the network.

Key queries (when data is populated)

// Full teaching lineage for a skill
MATCH path = (origin:Person)-[:TAUGHT*]->(leaf:Person)
WHERE ALL(r IN relationships(path) WHERE r.skill = 'causal-loop-diagramming')
RETURN path

// Open debts across the network
MATCH (p:Person)-[d:OWES]->(c:Organization {slug: 'commons'})
WHERE d.status = 'open'
RETURN p.name, d.skill, d.createdAt ORDER BY d.createdAt

// Most active mentors
MATCH (m:Person)-[:ATTESTED_TEACH_ONE]->(l:Person)
RETURN m.name, count(*) AS students_taught ORDER BY students_taught DESC

Marlowe — The Gate Execution Layer

Marlowe is a formal contract language for Cardano. In the RCN design, a symmetric three-handshake Marlowe contract governs SODOTO gate completion. When a gate completes in Marlowe, it triggers two things: Veramo issues the JWT, and the proxy writes the (:Credential) node to Neo4j. Marlowe provides the formal execution guarantee; Veramo provides the cryptographic signing; Neo4j holds the result.

The Marlowe contract source file (sodoto-mutual-certification.marlowe) is not currently on disk. This is a designed but unimplemented layer — current credential issuance is done manually by the coordinator without Marlowe enforcement.

Connection to the RCN Stack

SODOTO does not stand alone. It shares identity infrastructure with the CfA-dSC contracting system and both systems surface through FedWiki. Understanding the connections matters for coordinators running either tool.

Credentials authorize contract roles. A SODOTO credential establishes that a person is qualified to perform a particular skill professionally. A CfA-dSC contract for that service can reference the credential as qualification — the credential is the basis for trust between parties who may not know each other well.
TeachOne creates a debt to the commons. When SODOTO TeachOne completes, the student has received something of real value. In the designed graph model, a (:Debt) node is written to Neo4j — owed not to the mentor but to the commons. This debt is retired progressively: completing DoOne retires half, completing TeachOne retires the rest and creates a new debt for the student. The CfA-dSC three-currency model can make this economic relationship explicit — a gift of knowledge flowing from teacher to student, expressible later as time-dollars.
Shared DID infrastructure. Both systems use the same Veramo agent and the same Ed25519 key pairs. A person's DID in SODOTO is the same DID they use to sign CfA-dSC contract moves. The dids.json and people.json registries serve both systems — add a person once and they are available everywhere.
Both surface in FedWiki. SODOTO credentials appear as badge portfolio pages; CfA-dSC contracts appear as party-view contract pages. A practitioner's FedWiki presence can eventually show their full professional history: credentials earned, contracts performed, teaching relationships — all in one place.

For the full map of how all RCN tools relate, see the RCN Stack Overview. For the CfA-dSC system in detail, see cfa-dsc-intro.html.

What Is Not Yet Built

The following items are designed, partially built, or simply needed — but not yet complete as of June 2026.

HTTPS for multi-user access. The browser's Web Crypto API (used for Ed25519 signing) only works in secure contexts — HTTPS or localhost. On the current Mac Mini deployment, coordinators must use the Mac Mini's own browser. When deployed to a public server (DigitalOcean + Caddy + a domain), HTTPS is automatic and any coordinator can sign from their own machine.
DID onboarding for new practitioners. There is no defined self-service process for a new learner to get a DID. Currently the coordinator creates one via script and manually adds it to the registry files. A lightweight onboarding flow is needed.
v0.4 credential format. Planned additions: a learner JWT (the learner cryptographically acknowledges each passing gate attempt), a student JWT (the student signs their affirmation at TeachOne), and a Neo4j (:Debt) node created automatically when TeachOne completes — owed to the commons, retired progressively. None of these are in the current v0.3 format.
SODOTO Credential writes to Neo4j not yet wired. The proxy (sofi-proxy.py, running) already handles CfA-dSC Party/Contract nodes. Adding a /api/finalize-credential endpoint to write (:Credential), (:GateAttempt), and (:Debt) nodes from a SODOTO JWT is the next Neo4j task.
Marlowe gate execution not implemented. The designed architecture has Marlowe contracts governing gate completion and triggering Veramo + Neo4j writes. The Marlowe source file (sodoto-mutual-certification.marlowe) is not on disk. Current issuance is fully manual — coordinators run scripts without Marlowe enforcement.
Real gate histories on 7 credentials. Marc's CLD credential has full two-attempt attempt histories. The e-VSM, EIP, and Stock and Flow credentials have single clean-pass placeholder histories. Real dates, mentor names, and narrative page links are needed when available.
wiki-plugin-sodoto-badge source not committed to repo. The plugin source directory is installed in ~/.wiki/localhost/assets/ and ~/node_modules/ but the source has not been committed to ~/rcn. It needs to be staged and committed so the repo is self-contained.
CLI credential verification script. A coordinator tool that takes a signed credential JSON, extracts the signing payload, and confirms each Ed25519 proof against the issuer DID's public key — independent of the browser verify button. Useful for scripted audits.
CfA-dSC integration. The Dyadic Smart Contract system (Conversations for Action + three-currency settlement) is a related but separate tool stack. A contract creator UI exists at ~/rcn/tools/cfa-dsc-creator.html, Veramo DIDs are at ~/veramo-rcn/, and FedWiki party-view pages were working as of March 2026. The connection between CfA-dSC contracts and SODOTO credentials (e.g., credential issuance triggering a debt record) is designed but not implemented.
cfa-dsc-schema.json and validator library not in repo. The JSON schema and TypeScript validator (25 tests) for the CfA-dSC system were built in a prior session but are not present on disk. Need reconstruction or location and committing to ~/rcn.
