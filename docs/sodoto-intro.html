SODOTO — What It Is, How It Works, Where It Runs

A federated apprenticeship credentialing system. A skill is witnessed, practiced, and taught — then cryptographically certified by a Neighborhood Development Cooperative and published to a portfolio anyone can verify in a browser, with no server call and no login.

Technical reference · current as of August 2026 · supersedes all earlier SODOTO intro/context documents

What SODOTO Is

SODOTO issues verifiable digital credentials for practitioner skills. The credential documents not just that you have a skill, but how you acquired it: who showed you, who witnessed your practice, and who you subsequently taught. The chain of transmission is embedded in the credential and cryptographically signed by the issuing NDC organization.

The name comes from a medical training tradition: you observe a procedure done by an expert, you perform it yourself under supervision, and you teach it to the next learner. Each step is a gate. All three must pass before a full credential is issued.

Two properties make it different from an ordinary certificate:

  • Credentials are issued by cooperatives, not individuals. The signing authority is the NDC — persistent and institutional — not dependent on any one person. A mentor's departure never invalidates what they witnessed.
  • Verification needs no server. Anyone viewing a portfolio page can click Verify. The browser recovers the issuer's public key directly from its DID string and checks the signature. No registration, no login, no third party — permanently, for as long as the credential and its DID exist.

SODOTO is skill-agnostic. Each NDC defines its own list of skills to credential — systems-mapping tools, health-partner practices, trades, facilitation methods, anything a cooperative wants to transmit rigorously. The three-gate machinery is the same regardless of the skill. Anything that requires training can use SODOTO.

SODOTO stands alone. It needs no currency system, no health program, and no contract system to work. Those are separate, self-contained tools that can be used alongside it — the health-partner (CHW) program is one program that credentials with SODOTO; the three-currency agreements system (CfA-dSC) is a separate system anyone making agreements and exchanging value can use. They are examples of use, not dependencies. Each can stand on its own.

The Three-Gate Workflow

Every credential passes through three sequential gates. Gates cannot be skipped. A gate may take several attempts — the record of each attempt, including ended ones, is preserved as evidence of rigor.

Gate 1

See One

The mentor demonstrates the skill in a real working context. The learner observes closely. Both record a brief assertion — the mentor that they showed it, the learner that they understood — and the session is documented on a FedWiki narrative page.

Gate 2

Do One

The learner performs the skill themselves while the mentor witnesses. Both assert. If the mentor is not satisfied, the attempt is recorded as ended and another Do One is scheduled. There is no penalty for multiple attempts.

Gate 3

Teach One

The learner teaches a new student while the mentor witnesses the teaching. Both the mentor and the student attest. The student's own Do One page is the evidence record — you cannot claim Teach One without a real student who actually did the skill.

Where Every Piece Runs

Nothing SODOTO needs runs on a personal machine. The entire live system is three containers on the WikiCafe server plus each person's own web browser. A coordinator issues from their own browser; a learner or verifier views and verifies from theirs. Marc's development machine only builds the container images and pushes them to the registry — it is never in the running path, and if it were switched off the live system would keep working.

Why HTTPS matters. The browser's Web Crypto API — used for Ed25519 signing and verification — only works in a secure context (HTTPS or localhost). Because the WikiCafe deployment is HTTPS on a public domain, any coordinator can sign from their own machine. (An earlier localhost-only setup required signing on one specific machine; the WikiCafe deployment removed that limitation.)

Issuing a Credential — Coordinator Steps

The coordinator uses the browser-based issuer tool; it handles gate recording, signing, and every FedWiki write. No scripts or git commits. Full per-tab help is in the Issuer Tool Guide.

  1. Open the tool at sodoto.ndcgroup.relocalizecreativity.net/tools/sodoto-issuer.html. On first use it prompts for the write passphrase, which is kept only in that browser's local storage.
  2. Confirm the learner is registered. On the Registry tab, check they are listed; if not, add name, DID, FedWiki site, and portfolio slug. New entries sync to the server registry.
  3. Open the contract. On the Contract tab, pick the issuing NDC, the skill, and the learner, then Open / Resume. Gate state is tracked per issuer–skill–learner.
  4. Record each gate. For See One, Do One, Teach One, fill in date, mentor, both assertions, outcome, and narrative slug, then Record Attempt & Write to FedWiki. The tool writes to the learner's and mentor's portfolios immediately.
  5. Sign. On the Sign tab, review the preview, choose Full (all gates complete) or Partial, enter the NDC's 64-character hex key seed, and Sign & Issue. The JWT is signed in-browser with Web Crypto; the key is cleared right after and never sent anywhere.
  6. Badge is published automatically to the learner's portfolio and the ledger.
  7. Verify. Open the portfolio, click Verify on the new badge, and confirm ✓ Verified. A failure means the key seed did not match the issuing NDC's DID.
Two secrets, kept separate. (1) The write passphrase gates FedWiki writes and lives in the coordinator's browser storage. (2) Each NDC's Ed25519 private key seed — a 64-character hex string — signs credentials and must be kept in a password manager or Keychain. The tool never stores the key seed. If a seed is lost the NDC can no longer sign under that DID, but already-issued credentials remain valid forever (they verify from the public key encoded in the DID).

How Verification Works

The did:key format encodes the issuer's public key directly in the DID string, so no lookup is ever required. When a user clicks Verify, the sodoto-badge plugin, entirely in the browser:

  1. Reads the jwt from the badge markup and splits it into header, payload, signature.
  2. Decodes the payload and reads iss — the issuer's did:key string.
  3. Decodes the DID's multibase suffix back to the raw Ed25519 public-key bytes.
  4. Calls crypto.subtle.verify() over header.payload with the decoded signature.
  5. Reports ✓ Verified or ✗ Failed.

The JWT is the credential. If the badge renders and Verify passes, it is authentic and unmodified — with no server, no expiry, and no third party.

The Portfolio Page

Each learner has a FedWiki portfolio page that displays their badges. Pages are written by sofi-proxy into the shared volume and served by FedWiki. Each badge, rendered by the sodoto-badge plugin, shows the skill and issuing NDC seal, the three gate dates, mentor name(s) linked to their own portfolios, the full attempt history per gate, and a Verify button. Long badges collapse into an accordion, and the mentoring log groups attempts by learner and skill, most-recent first.

Live demo cast. The public WikiCafe site is seeded with a clearly-labelled demo cohort (a DEMO Academy issuer and demo learners such as demo-alex-rivera) so the system can be shown end-to-end without exposing real people. Seeding is opt-in via SEED_DEMO, writes only files that are absent, and never overwrites real content. A production NDC simply leaves SEED_DEMO unset.

Skills

SODOTO does not fix a skill list — each NDC credentials whatever it chooses. Two example families:

  • Systems-mapping tools (RCN): Causal Loop Diagramming, e-VSM, EIP, Stock-and-Flow, OPM, the Vester Sensitivity Model, and others in the RCN toolset. The Vester cluster (nine interacting skills) will need a credential-cluster design before individual credentials are issued.
  • Health-partner practices (a health NDC): skills such as Health Picture Review or care-plan note-writing — one cooperative's chosen skill set, credentialed with the same three gates. These belong to that NDC's program, not to SODOTO itself.

Whether a credential maps to a pay tier, a role, or nothing at all is a policy choice made by each cooperative — it is layered on top of SODOTO, not part of it.

The Teaching Graph (designed)

SODOTO is designed to write its data into Neo4j so teaching chains and credential provenance are queryable — node types (Person, Skill, Credential, GateAttempt, Organization) and their relationships are specified; the writes are part of the Neo4j work above. This is provenance, and it stands on its own.

A separate, optional layer can attach an economics to teaching: when Teach One completes, real value has changed hands. If a cooperative wants to make that explicit it can record a debt owed to the commons (not to the mentor), retired progressively — Do One retires half, Teach One retires the rest and creates a new debt for the student, forward-propagating with no cycles. That debt-and-value model is part of the separate agreements/currency system below, not something SODOTO requires.

How It Composes With Other RCN Tools

SODOTO stands alone, and so do the tools it can be paired with. It shares Ed25519/DID identity infrastructure with the CfA-dSC agreements system — a separate, self-contained tool for making agreements and exchanging value with a three-currency settlement — and both happen to surface through FedWiki: credentials as portfolio pages, agreements as party-view pages. Because they share identity, a cooperative that wants to can connect them (a credential qualifying a contract role; a Teach One recorded as a value exchange) — but neither depends on the other, and each is fully usable without the rest. These are examples of composition, not requirements. For the full map, see the RCN Stack Overview.
