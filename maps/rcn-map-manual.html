    RCN NDC Map — User Manual

    Complete reference for all features

    Updated July 2026  ·  Introduction →
    Getting Started

    1. Interface overview

    The tool is a single HTML file paired with a data file (rcn_static_data.js). Open rcn_map.html in any modern browser. Both files must be in the same folder, or the map will load without any NDC or geographic data.

    Two ways it's packaged: rcn_map.html vs rcn_map_standalone.html

    Same tool, two forms — pick by how it's being used:

    FileWhat it isUse it for
    rcn_map.html The source page. Loads rcn_static_data.js (a separate ~5.5 MB file) from the same folder, and fetches issues from a hosted index. The live site — a two-file deploy (rcn_map.html + rcn_static_data.js) in one asset folder. Edits re-upload just the small HTML file.
    rcn_map_standalone.html A built, self-contained copy with the data (and issues) inlined — one ~5.9 MB file, no companion needed. Produced from the source by build_standalone_map.py. A handout — email it, drop it on a USB stick, or open it straight from your desktop. Give a steward the whole tool + data in one file.
    The two are not interchangeable as the baseline: never replace rcn_static_data.js with either of these, and remember the standalone is a snapshot — it won't reflect edits to the source until build_standalone_map.py is re-run. Either way, Leaflet and the map tiles still load from the internet, so "self-contained" means "no companion files," not "works offline."
    Don't put the standalone at your live URL and keep editing the source — they'll drift. Serve rcn_map.html as the canonical live page; use the standalone only as a portable copy.

    How old is this copy? Every standalone build stamps its own build date into the sidebar, just under the Intro / Manual / Slides links — so a handout that has been sitting in someone's inbox says so on its face, and turns red past 90 days. The live rcn_map.html shows no stamp: it isn't a snapshot, it's the source.

    Its doc links keep working. The sidebar's Intro / Manual / Slides links are relative on the live page, because those files sit beside it in the same asset folder. A handout travels alone, with no siblings to resolve against — so the build rewrites those three links to their hosted copies at ndcgroup.relocalizecreativity.net/assets/NDC/. Anyone who opens the emailed file can still reach the docs. (Set RCN_DOCS_BASE before building if the asset folder ever moves.)

    What rcn_static_data.js is

    rcn_static_data.js is the map's baseline data file — the geography the map draws before you add anything. It holds the built-in NDCs and all their geographic context layers (admin boundaries, ecological zones / watersheds, NDC zone polygons, mineral-deposit points, churches) as JavaScript variables the map reads on load. It's a .js file (loaded via <script src>) rather than a .json file so the map also works opened straight from disk. It is generated once from the RCN geo database by generate_static_data.py (see §16) — not hand-edited.

    The RCN base vs. your additions — two separate layers

    This is the most important distinction in the tool. What you see on the map is two layers stacked together, and they are never mixed:

    The RCN baseYour additions
    WhatBuilt-in NDCs + geographic context layersCustom NDCs, boundaries, location pins, NDC location corrections
    Lives inrcn_static_data.js (+ the built-in NDC_LIST in rcn_map.html)Your browser's localStorage — on this device, in this browser only
    Who sees itEveryone who opens the mapOnly you (until you export & publish it — §18)
    Editable in the map?No — read-only to usersYes — add, ✎ Edit, remove freely
    Changed byA maintainer, in the source (see below)You, right in the map UI
    Nothing you do in the map changes the RCN base. Adding an NDC, drawing a boundary, dropping a pin, even correcting an NDC's location — all of it is written to your localStorage layer, sitting on top of the shared base. Other people's maps are unaffected. This is deliberate: you can experiment freely without touching the network's shared data.

    How & who can change the RCN base

    Changing the base is a deliberate, source-level act — it cannot happen by accident through the UI. There are two ways, both done by whoever maintains the deployed files:

    • Add/adjust a built-in NDC — edit the NDC_LIST array in rcn_map.html (§14), then re-deploy the file.
    • Change boundaries or context layers — update the RCN geo database and re-run generate_static_data.py to rebuild rcn_static_data.js (§16), then re-deploy it.
    Corrections look like base edits but aren't. When you use 📍 Correct location on a built-in NDC, the corrected position is saved to your localStorage (rcn_ndc_corrections) and overrides the display for you only. To make a correction permanent in the base, export it (§12) and hand it to whoever maintains rcn_static_data.js, so the fix goes into the source.

    The interface has two areas:

    • Map canvas — fills the full browser window. Powered by Leaflet.
    • Sidebar — a panel overlaid in the top-right corner. Contains the NDC list, legend, and OSM search. Scrollable when content is long.

    Two controls appear on the map itself, top-left: a zoom control (+/−) and a layer control (the stacked-layers icon) for switching basemaps.

    The tool loads in Overview mode — all 7 NDC markers visible, map fitted to show them all. This is always the starting state.

    Viewing NDCs

    4. Network overview

    The Overview — all NDCs button at the top of the sidebar resets the map to show all seven NDCs simultaneously. The map fits its bounds to include all NDC markers with padding. This is also the initial state when the page loads.

    In overview mode, all geographic context layers (admin boundaries, ecological zones, NDC zone polygons, mineral deposits, churches) are drawn for all NDC buckets at once. The legend in the sidebar lists all features grouped by bucket (state, country, or custom label).

    Click any red NDC circle marker on the map to open a popup with the NDC's name and address. To zoom into an NDC's region, use the NDC accordion in the sidebar rather than clicking the marker.

    5. NDC accordion

    Below the Overview button, the sidebar lists all NDCs as an accordion. Each row shows the NDC name and location.

    1. Click an NDC row to expand it. The row highlights in green and an arrow changes from ▶ to ▼.
    2. The map zooms to fit the polygons for that NDC's state.
    3. Geographic context layers for that state load into the map.
    4. A legend specific to that NDC's state appears inside the accordion body.
    5. If the NDC has any issues, an Issues sub-section appears inside the accordion.

    Only one NDC can be expanded at a time. Clicking a second NDC collapses the first. Clicking the expanded NDC again collapses it and returns to overview.

    The per-NDC legend appears inside the accordion, not in the bottom legend area. The bottom legend area is hidden while an NDC is expanded.

    6. Geographic layers

    Each NDC has geographic context features drawn on the map. These come from rcn_static_data.js — pre-generated from the RCN geo database. Features are categorized by place_type and rendered in consistent colors:

    Layer typeColorStyleWhat it shows
    Admin boundary Blue Polygon outline, 12% fill Municipal, county, or regional administrative boundaries
    Ecological zone Purple Polygon outline, 12% fill Watershed, forest, conservation, or ecological district boundaries
    NDC zone Red-orange Thicker polygon outline, 18% fill The NDC's own operational or site boundary
    Mineral deposit Bronze Circle marker (small dot) Copper deposit points — relevant for mining-adjacent communities (Superior AZ)
    Church Violet Circle marker (larger, white border) Churches — part of the community asset inventory

    Polygons are sorted largest-to-smallest before drawing so that smaller features are not obscured by larger ones. Click any polygon or marker to open a popup with its name, type, area (for polygons), and boundary source.

    7. Legend & highlighting

    Each NDC's geographic layers are its own key: expand an NDC in the sidebar accordion to see and highlight them. (There is no separate always-on flat legend — that was removed as redundant.) Everything you add — custom boundaries, pins, and federated regions — is listed once in a collapsible My additions & layers section, never repeated under each NDC. All panels start collapsed.

    Export a picture of the map. The small ↧ SVG, ↧ PNG, and 🖨 Print buttons near the top of the sidebar save the current view. SVG/PNG capture the overlays (boundaries, NDCs, pins, issue areas) on a plain background — basemap tiles can't be exported. Print uses your browser to print the full map with the basemap (choose "Save as PDF" for a file). The full Issue Map has the same three buttons in its toolbar.

    Single highlight

    1. Click any legend item. That feature becomes fully opaque and highlighted; all others dim to near-invisible.
    2. The map zooms to fit the highlighted feature.
    3. Click the same item again to clear the highlight and restore all features.

    Multi-select highlight

    1. Click a legend item to highlight it.
    2. Shift+click additional items to add them to the selection.
    3. The map zooms to fit all highlighted features simultaneously.
    4. Shift+click a highlighted item to deselect just that one.

    The hint text at the bottom of the sidebar (Click to highlight · Shift+click to multi-select) is a persistent reminder of this behavior.

    Use multi-select to compare two features — for example, select both an admin boundary and an ecological zone to see where they overlap.
    Issues

    8. Issue overlay

    Issues are community questions, campaigns, or decisions that an NDC is engaged with — zoning changes, land-use proposals, neighborhood initiatives. Each issue has parcel-level data: which properties are affected and what stance each parcel holder takes.

    Viewing an issue

    1. Click the NDC that has the issue to expand its accordion.
    2. If the NDC has issues, an Issues sub-section appears with a count badge.
    3. Click Issues ▶ to expand the sub-section and see the issue list.
    4. Click an issue button (e.g., 📍 Backyard Chickens) to load the issue overlay.

    The overlay draws three layers on the map:

    LayerStyleWhat it shows
    County boundary Purple dashed outline, 3% fill The county containing the issue area
    Municipality boundary Orange dashed outline, 5% fill The city or town boundary
    Issue area polygon Yellow dashed outline, 10% fill The specific geographic area the issue concerns (neighborhood, zone, district)
    Parcel markers Circle markers color-coded by stance Individual properties: green = pro, red = con, grey = unknown

    Click any parcel marker to see its label, stance, and any notes. The map zooms to fit the issue area polygon when an issue is first loaded.

    Clearing an issue

    Click the active issue button again to remove the overlay. The button highlights while the issue is active.

    Network issues — kinds, links, and the Graph Tool

    Some issues are networks rather than for-and-against questions: a directory of co-ops and who funds, supplies or built whom (📍 Co-ops of Whatcom County, under East Whatcom RRC). In these, dots are coloured by kind instead of stance, lines join the points, and a legend sits at the top left. Click any line to see what the tie is and where the claim came from. The map frames the dots rather than the whole area, so short links in town are not hidden under their own dots.

    The legend has two more controls:

    • 🕸 Open in Graph Tool — opens the same points and lines as an editable diagram in the RCN Graph Tool, in a new tab: same colours, same legend, laid out like the map with overlapping points nudged apart. Each node keeps its notes, its coordinates, and an _onMap link that brings you back to that spot on the map. Use the Graph Tool's Force or Untangle layout to rearrange by connection instead of geography.
    • ⬇ graph JSON — saves the same diagram as a Graph Tool file, to import later or drop into FedWiki.

    The map stays the source. The diagram is a copy to work on; edits in the Graph Tool do not flow back to the issue file.

    On a deployed site the button looks for graph-tool-v22.html in the same asset folder as the map. Upload the self-contained build from tools/dist/, never the raw tool, or its icons silently disappear. Add ?graphtool=<URL> to the map's address to point it somewhere else.
    Issue data is fetched at runtime from a URL configured in the ISSUE_INDEX array in the HTML file. If the URL is empty or unreachable, the overlay will not appear and an error is logged to the browser console.

    9. Issue full map link

    When an issue is active (its overlay is showing), a link appears below the issue button: → Open full Issue Map. This opens issue-polygon-map.html for that specific issue in a new tab.

    The issue-polygon-map.html tool is the editing environment for issues: it lets you draw and edit parcel polygons, record stances and notes, import and export GeoJSON, and switch basemaps. Custom boundaries drawn there can now be named and renamed — finishing a draw prompts for a name, each polygon's popup carries a Rename button, and the name round-trips through GeoJSON export/import. The NDC map lets you add locations, boundaries, NDCs, and issues, but it does not edit an issue's parcels — that editing happens in the issue-polygon-map.

    The link is only active if a map URL is configured in the issue's ISSUE_INDEX entry. If no map URL is set, the link appears greyed out.

    Search

    10. OSM geocoder search

    A search bar at the top of the sidebar lets you find any location worldwide using the OpenStreetMap Nominatim geocoder.

    1. Type any address, place name, or landmark in the search field.
    2. Press Enter or click Go.
    3. Up to 5 results appear in a dropdown below the field.
    4. Click any result — the map flies to that location and drops a blue marker.

    The search marker stays on the map until you search for something else or reload the page. Only one search marker exists at a time — a new search replaces the previous marker.

    Clearing the search field hides the results dropdown immediately. Clicking anywhere outside the search box also closes the dropdown.

    Nominatim search requires an internet connection — it is the one feature that does not work offline. NDC data, geographic layers, and issue data (if bundled) work offline.
    Editing

    11. Adding custom location pins

    The + Add location button lets you drop a named pin anywhere on the map. Pins are saved in your browser and appear alongside NDC markers in the legend.

    How to add a location

    1. Click + Add location in the sidebar. A green banner appears; cursor becomes a crosshair.
    2. Click anywhere on the map — including over polygon overlays. A small form appears near the click point.
    3. Type a name for the location and click Add (or press Enter).
    4. A sky-blue circle marker appears at the clicked position. It is added to the legend under "Custom locations" with a + badge.

    Editing, moving, or removing a custom pin

    In the legend under Custom locations, each pin has an ✎ Edit link that opens an inline editor to rename it and recolour it — the change updates the legend and the map marker live. To move the pin, click it on the map and use 📍 Correct location in its popup (same crosshair flow as NDC corrections). × (in the legend) or Remove (in the popup) deletes it.

    Persisting your pins

    Custom pins are saved to localStorage. The quickest way to back them up is the top-level ⬇ Export my data (JSON) button near the top of the sidebar (just under + Add location), which downloads everything you have added — NDCs, locations, boundaries, and corrections — as one file. To export just the pins, open Add boundary layer → Saved and click Export locations.

    Custom pins are per-browser. Opening the map in a different browser will not show your pins unless you re-import from an exported JSON.
    Editing

    12. Correcting NDC locations and custom pins

    NDC marker positions come from the static data file, and custom pin positions are set when you first place them. If either appears in the wrong spot you can correct it directly in the map without editing any files. Corrections are saved in your browser and applied automatically every time you open the map.

    How to correct a location

    1. Click a red NDC marker or a sky-blue custom location marker on the map to open its popup.
    2. Click 📍 Correct location in the popup.
    3. A yellow banner appears at the top of the sidebar. The map cursor changes to a crosshair.
    4. Click the correct position on the map. The marker moves immediately.

    You can click anywhere — including on top of a boundary polygon, a reach-area band, a route line, or another marker. While the yellow banner is up, the whole map is a placement surface, so nothing on it can intercept the click or open its own popup instead. Cancel stops it completely: once cancelled, later clicks on the map go back to doing their normal thing and nothing moves.

    Resetting a correction

    Open the corrected marker's popup — it shows "✓ Location corrected — reset". Click reset to remove the correction and restore the original position. You can also find all corrections in the Add boundary layer → Saved tab and remove them there.

    Saving corrections permanently

    Corrections live in your browser's localStorage. To back them up, use the top-level ⬇ Export my data (JSON) button (which includes corrections along with everything else), or open Add boundary layer → Saved and click Export corrections for just the corrections. Either downloads a JSON file you can give to whoever maintains rcn_static_data.js so the fix goes into the source data.

    Corrections are per-browser. If you open the map in a different browser or on a different machine, the correction won't be there until the source data is updated or the correction is applied again.
    Editing

    13. Adding boundary layers

    The Add boundary layer panel lets you add any polygon boundary to the map — a county, city limit, watershed, national forest, or any custom area. Added layers appear in the legend with a group-bucket badge, support highlighting, and persist across page reloads. You can draw one freehand, or use the two tabs below.

    Click Add boundary layer ▶ in the sidebar to expand the panel.

    Edit a boundary after you make it. Every boundary in the legend has an ✎ Edit link that opens an inline editor for all of its metadata — name, type, group bucket, colour, fill opacity, and Under NDC. The Under NDC field files the boundary inside that NDC's section of the legend (instead of the flat "My additions & layers" list), or set it to "— none —" to keep it loose. The draw and paste forms also carry an Under NDC field so you can set it at creation. Every choice is saved with the boundary; changes update the map live.

    Search OSM tab

    Finds real boundary polygons directly from OpenStreetMap for any named jurisdiction.

    1. Type a place name in the search field (e.g. Pinal County AZ, Ingham County Michigan, Cascade River State Forest).
    2. Click Search. Results that have actual polygon boundaries appear in the list — point-only results are filtered out.
    3. Click a result to preview the polygon on the map (shown in green dashes).
    4. A form appears pre-filled with the name. Adjust the name, type, and state group if needed, then click Add to map.
    OSM has polygon boundaries for most US counties, cities, national forests, parks, watersheds, and many other named areas. If a search returns no polygon results, try a more specific name or check the Ask Claude tab.

    Ask Claude tab

    For boundaries that aren't in OpenStreetMap — custom districts, informal areas, boundaries from other sources — use the Claude prompt helper.

    1. Describe the boundary you need (e.g. Superior AZ city limits, the Tonto National Forest boundary near Superior AZ).
    2. Click Build prompt. A formatted prompt appears.
    3. Click Copy prompt, go to claude.ai, start a new conversation, and paste.
    4. Copy Claude's JSON response and paste it into the response field.
    5. Click Import polygon.
    Claude generates approximate polygon coordinates — good for visual reference and orientation on the map. For precise legal or regulatory boundaries, use the OSM search or import an authoritative GeoJSON file.

    Saved tab

    Lists all user-added polygons and location corrections. Click × next to any entry to remove it. The tab has four granular export buttons — Export locations, Export polygons, Export NDCs, and Export corrections — each downloading just that dataset as JSON.

    For a one-file backup of everything you have added (NDCs, locations, boundaries, and corrections together), use the top-level ⬇ Export my data (JSON) button near the top of the sidebar instead. It writes a single rcn-map-data.json bundle.
    Maintenance

    14. Adding an NDC

    There are two ways to add an NDC: the Add NDC panel in the sidebar (for a personal NDC saved in your browser) and editing NDC_LIST in the source (for a built-in NDC everyone sees).

    In the app — Add NDC panel (no coding)

    1. Expand Add NDC in the sidebar.
    2. Enter a name, a location (shown after the name), a code (the group bucket — see below), and set the pin (type coordinates or click Set from map).
    3. Click Add NDC. It appears in the accordion and on the map, and is saved in your browser (rcn_user_ndcs).

    Editing a saved NDC. Expand Saved NDCs inside the Add NDC panel. Each NDC you added has an Edit link (rename the name or fix the location text — useful if a stray URL lands in a field) and a × to remove it. Built-in NDCs are fixed and have no Edit link.

    Code = group bucket. The code is a free-text grouping label, not a validated geography — up to 32 characters, in any case. Use a US state (WA), a country (ES), or your own label (Whatcom, Nooksack). NDCs and boundaries that share the exact same bucket string are grouped together in the legend.

    In the source — built-in NDC

    Built-in NDCs are entries in the NDC_LIST array near the bottom of rcn_map.html. A minimal entry is three fields; add lat/lng/address to place the pin without touching the geo database:

    { name: "NDC Name", state: 'XX', label: "NDC Name — City, State",
  lat: 48.749, lng: -122.478, address: "City, State" }
    FieldDescription
    nameDisplay name. If the NDC's point comes from the static data, must match the name in RCN_NDCS.
    stateThe group bucket (see the tip above). Boundaries/layers sharing this exact string group with this NDC.
    labelText in the sidebar accordion — typically "NDC Name — City, State".
    lat/lng/addressOptional. If present, injectExtraNDCs() adds the map pin at startup — no geo-database entry needed (this is how Porthmadog, Alpujarra, and Main Street Bellingham are placed).
    A built-in NDC with no lat/lng only affects the sidebar until its point and context layers are added to the geo database and rcn_static_data.js is regenerated (section 16). NDCs with lat/lng in NDC_LIST place their own pin.
    Maintenance

    15. Adding an issue

    Issues are community questions mapped to a place — zoning decisions, land-use campaigns, access gaps. The New issue panel now has two independent actions, so creating an issue never depends on AI or a network connection.

    Create issue — no API key, works anywhere

    1. Expand New issue in the sidebar.
    2. Type a title, pick the NDC, and (optionally) paste addresses one per line as 52 N Pinal Ave — pro (pro / con / unknown).
    3. Click Create issue. The issue appears on the map immediately — a default affected area drawn around the NDC, with a coloured pin per address. It's listed under that NDC's Issues.
    4. Refine the shape and parcel positions later in the full Issue Map (issue-polygon-map.html).

    Draw area with Claude — optional

    Below Create issue is an optional ✨ Draw area with Claude step. Paste your Anthropic API key (stored locally in your browser) and click Generate area + stances with Claude; Claude draws the real affected-area polygon and infers stances for addresses you didn't classify. The result shows on the map the same way.

    Where the issue is saved

    On a local setup with sofi-proxy running, a created/generated issue is written to disk (tools/issue-data/) and persists across reloads. On a deployed site there's no write proxy, so the issue is downloaded as a JSON file for you to publish to your issue host — and it shows in the current session immediately regardless.

    Prior issues (e.g. Backyard Chickens) load from the issue index. On a deployed single-file map they are bundled into the file at build time (build_standalone_map.py), so they appear with no hosting.

    What Claude generates

    The prompt asks Claude for a JSON object with: meta information (title, community, NDC, description, date), an issue polygon (approximate lat/lng coordinates around the affected area), and a list of parcels with stances (pro/con/unknown). Claude estimates coordinates from its knowledge of the area. Refine them later in issue-polygon-map.html. 

    {
  "meta": { "id", "title", "community", "ndc", "coordinator", "date", "status", "description" },
  "issue": { "centroid": [lat, lng], "polygon": [[lat,lng], ...] },
  "parcels": [{ "id", "label", "latLng": [lat,lng], "stance": "pro/con/unknown", "notes" }]
}

    Refining an issue in the editing tool

    After importing, click → Open full Issue Map next to the issue name. This opens issue-polygon-map.html, which lets you: drag parcel markers to correct positions, edit stances and notes, draw or adjust polygons, and export the refined JSON. Save the exported JSON back to tools/issue-data/{key}.json to update what the map loads.

    The issue-index.json file

    All issues are registered in tools/issue-data/issue-index.json. The Import button updates it automatically. To remove an issue, delete its entry from that file and remove the JSON file from tools/issue-data/. To add an issue from a different source (e.g., a JSON file you built manually in issue-polygon-map.html), add an entry to issue-index.json directly: 

    { "key": "az--my-issue", "label": "My Issue", "ndc": "Leo's NDC",
  "url": "http://localhost:8765/tools/issue-data/az--my-issue.json",
  "map": "http://localhost:8765/tools/issue-polygon-map.html?issue=az--my-issue" }
    Issue index and data files live in tools/issue-data/. They are served by sofi-proxy and loaded fresh each time the map opens. There is no need to rebuild rcn_static_data.js for issues.

    16. Updating geographic data

    The map's geographic layers — admin boundaries, ecological zones, NDC zone polygons, mineral deposits, and churches — come from rcn_static_data.js in the maps/ folder. This file is auto-generated and should not be edited by hand.

    Data files

    FilePurpose
    maps/rcn_static_data.js Generated output — all geographic features as a JavaScript file. Exports two variables: RCN_PLACES (GeoJSON FeatureCollection of all place features) and RCN_NDCS (GeoJSON FeatureCollection of NDC point locations).
    maps/generate_static_data.py Python script that queries the RCN geo database and writes rcn_static_data.js. Run this whenever the source database changes.

    Regenerating the static data

    1. Update the source geo database with any new features, boundary changes, or new NDC locations.
    2. Run python3 maps/generate_static_data.py from the rcn/ root directory.
    3. The script overwrites maps/rcn_static_data.js.
    4. Reload rcn_map.html in the browser — new features appear immediately.

    Feature properties

    Each feature in RCN_PLACES needs these properties to render correctly:

    PropertyTypeDescription
    namestringDisplay name (shown in popups and legend)
    statestringState/country code — groups features in the legend (AZ, MI, WA, TX, GA, WLS)
    place_typestringOne of: admin_boundary, ecological_zone, ndc_zone, mineral_deposit, church
    area_mi2numberArea in square miles — used for polygon draw order (largest drawn first)
    boundary_sourcestringAttribution shown in popups (e.g., "OpenStreetMap", "USGS")

    Each feature in RCN_NDCS needs:

    PropertyTypeDescription
    namestringNDC name — must match the name field in NDC_LIST
    statestringState/country code — used to filter NDC markers in per-NDC view
    addressstringStreet address shown in the marker popup
    The geometry for RCN_NDCS features must be GeoJSON Point type with coordinates in [longitude, latitude] order (GeoJSON standard).

    17. Sharing & deep links

    Every polygon, NDC marker, issue overlay, and custom location has a shareable URL you can copy directly from its popup. Links open the map to that exact feature — no manual navigation needed.

    Copying a link to a specific feature

    1. Click any polygon boundary, NDC marker, user polygon, or custom location pin to open its popup.
    2. Click 🔗 Copy link in the popup. The URL is copied to your clipboard.
    3. Paste it anywhere — message, doc, email. Anyone with access to the map server can open it.

    When the recipient opens the link the map loads, zooms to that feature, and highlights it automatically.

    Copying the current view

    The 🔗 Copy view link button (bottom-right corner of the map) captures whatever center and zoom level you're looking at, independent of any specific feature. Useful for sharing a context — "here's roughly where we're working."

    URL parameter reference

    ParameterEffectExample
    ?highlight=NAMEZoom to and highlight a named polygon (admin boundary, ecological zone, NDC zone)?highlight=Pinal+County
    ?highlight=ndc:NAMEFly to a specific NDC marker?highlight=ndc:Leo%27s+NDC
    ?openissue=KEYLoad and display an issue polygon overlay by issue key?openissue=az--chickens
    ?lat=&lng=&zoom=Fly to specific coordinates at a given zoom level?lat=33.295&lng=-110.983&zoom=14

    Notes

    • Links to static named polygons and NDCs work for anyone on the same server.
    • Links to user-added polygons (user:N) and custom locations (loc:N) only work on the same device — that data lives in localStorage, not the server.
    • Parameters can be combined: ?openissue=az--chickens&lat=33.295&lng=-110.983&zoom=15 will load the issue overlay and fly to the given view.
    Federation

    18. Publishing & federating regions

    Everything you add lives in your browser. To share it — so other people's maps show your NDCs, boundaries, and pins — you publish it as a region file and list it in a manifest (regions.json). Each map reads the manifest on load and pulls in every region as read-only overlays. This is how regional stewards (e.g. Jerry / Michigan, Chris / Arizona, Marc / Whatcom) stitch their areas into one shared network map.

    Two different files: a region file is your data (it's exactly what ⬇ Export my data writes); regions.json is a small roster that points at one or more region files. Do not overwrite rcn_static_data.js (the baseline) with either — they're separate.

    Step by step

    1. In the map, click ⬇ Export my data (JSON) → you get rcn-map-data.json. Rename it to something regional, e.g. whatcom-region.json.
    2. Upload that region file into the assets folder (the same place rcn_map.html lives).
    3. Open the Publish regions (federation) panel. Add a row per steward — Region label, optional Steward, and the File / URL (just the filename if it's in the same folder, or a full https://… URL if it's on another steward's site).
    4. Click ⬇ Generate regions.json → it downloads the assembled manifest.
    5. Upload regions.json into the same assets folder.
    6. Reload the map. It fetches regions.json, pulls each region file, and lists them under “Federated regions (read-only)” in the legend.
    A web page cannot write files to the server — that's a browser security boundary. So the Publish panel can only generate regions.json and hand it to you; you upload it (and the region files) into the assets folder. Likewise, collecting other stewards' region files and placing them in your folder is a manual step.

    Things to know

    • Read-only. Federated regions can be viewed and highlighted but not edited on your map — they're published copies, not your working draft.
    • Boundary→NDC nesting doesn't travel. The Under NDC field is a local view setting; in a region file, boundaries appear under the "Federated regions" heading, namespaced by region.
    • More stewards = more rows. Add a line per steward; each entry's url can be a flat filename (same folder) or a full URL (their own host).
    • Corrections aren't published — only NDCs, boundaries, and locations are read from a region file.
    A forward-looking design — replacing the hand-maintained manifest with FedWiki's native fork gesture (forking a steward's region page = adding their region, with full provenance) — is written up in rcn-region-forking-spec.md.
    Drawing

    19. Routes — drawn and found

    A route is an open line, as opposed to a boundary's closed ring: a walking route to school, a delivery run, a corridor. There are two buttons, and the difference between them matters more than it looks.

    ButtonWhat the line isWhen to use it
    ➤ Draw a route Exactly the points you click. Nothing is snapped, routed, or calculated. An assertion — the way people actually walk, a desire path, a route that isn't in any map yet, a line across a field.
    ➤ Find route The route a routing engine returns along real roads and paths between your points. A question answered — how far is the clinic on foot, what would a delivery van do, how long is the ride.

    Finding a route

    1. Click ➤ Find route (walk / bike / drive). A panel appears at the top of the map.
    2. Pick a profile: 🚶 Walk, 🚲 Bike, or 🚗 Drive. Walk is the default — it's the neighborhood question.
    3. Click a start and an end on the map. Any further clicks become stops along the way, in order.
    4. Click ➤ Find route (or press Enter). The engine returns the actual route, and the panel reports distance and travel time.
    5. Name it, colour it, and save it exactly like a drawn route — same form, same legend, same export.

    Undo removes the last point (Backspace / Ctrl+Z), Esc cancels. Double-click does not trigger a search — finding a route makes a network request, so it always takes a deliberate click.

    A found route is a different kind of object

    Once saved, both kinds behave identically — legend row, colour and dash editing, direction arrows, deep link, JSON and SVG/PNG export. But a found route records where it came from, and its popup says so: the profile, the engine, and the date it was computed. A drawn route just says Hand-drawn.

    That distinction is deliberate. A drawn line is something a person claims. A found line is derived — it came from OpenStreetMap data on a particular day, it can change when that data changes, and it can be wrong. The saved date is what lets you tell later whether a route still means what it meant when you saved it.

    What it needs, and how it fails

    Routing is provided by Valhalla on the FOSSGIS public instance, using OpenStreetMap data. There is no account, no API key, and nothing to configure — but it is a shared community service with no service guarantee, and it needs an internet connection.

    • No connection — you're told to check it, or draw the route by hand instead. Your points stay on the map.
    • A point too far from any road or path — "No suitable edges near location." Move that point nearer a road.
    • Points too far apart — there's a 200 km limit per route.

    In every failure the panel stays open with your waypoints intact, so you can undo a point, switch profile, or retry. Nothing is ever saved from a failed search.

    A standalone handout can still show saved routes offline, but it cannot find new ones without a connection — the same as the basemap tiles.

    20. Reach areas (isochrones)

    A route answers how do I get from here to there. A reach area answers the question a neighborhood actually asks: what can be reached from here at all? Place one centre — an NDC, a clinic, a school, a bus stop — and the map shades the area you can genuinely get to within a given number of minutes, following real streets and paths. The technical name is an isochrone: a line through all the points that are the same travel time away.

    This is the "15-minute neighborhood" made checkable. A circle drawn with a compass says nothing — it ignores the river, the freeway, the missing sidewalk, the fence. A reach area shows those as dents in the shape.

    Making one

    1. Click ◎ Reach area (how far in N minutes).
    2. Pick 🚶 Walk, 🚲 Bike or 🚗 Drive. Walk is the default.
    3. Pick the times you care about — up to four bands at once (the routing service's limit). 5 / 10 / 15 minutes is the default set.
    4. Click the map to place the centre. Click again to move it.
    5. Click ◎ Show reach area (or press Enter).
    6. Give the set one name and save. Each band becomes its own boundary layer, named with its time — "Superior clinic — 10 min walk".

    They are ordinary boundaries afterwards

    Each band is saved as a normal boundary polygon, so everything the map already does to boundaries works on them: its own legend row, the ✎ Edit editor for name, colour, opacity and which NDC it sits under, highlight on click, deep link, and inclusion in JSON and SVG/PNG export. Bands are coloured darkest-innermost and saved largest-first so the smaller ones draw on top; delete any band on its own without touching the others.

    Like a found route, a reach area records where it came from — profile, minutes, engine, centre, and the date it was computed — and its popup says so. A boundary you drew or pasted still reads User-added. The two look similar on the map and mean very different things: one is a claim about the world, the other is an estimate derived from OpenStreetMap on a particular day.

    Limits worth knowing before you show one to a room

    • It's a road-network estimate, not a promise. It assumes an average traveller at an average speed. It knows nothing about a person's mobility, a pram, ice on the path, or whether the sidewalk is lit at night.
    • It's only as good as OpenStreetMap. A footpath nobody has mapped doesn't exist to the engine; a path that's mapped but gated does. Where the shape looks wrong, that is often worth knowing in itself — and it's a reason to add the missing path to OSM.
    • An unreachable centre gives nothing. Drop the centre in open water or far from any road and you're told nothing is reachable — the map refuses to save a meaningless speck.
    • Four bands maximum per request, and it needs an internet connection.

    Two reach areas from the same centre — walk versus drive — put the transport gap in a single picture better than any table. So does one reach area against the households it's supposed to serve.
