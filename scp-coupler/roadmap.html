SCP + PKC Integration — Prospective Work

Where We Are

The SCP-PKC experiment is running. A Problem-Knowledge Coupler embedded in a FedWiki page can read health-log and visit context, generate structured SOAP-format assessments, push them to the patient's wiki, and narrate a pre-visit summary — all from within the care plan.

The table below reflects current status across the three integration steps that were planned at the outset:

Step Description Status
1 FedWiki export — push structured SOAP assessment to patient wiki page Done
2 SCP context pull — inject health-log, visits, and about-me into Claude frame calls Done
3 PKC landing page — embed coupler in FedWiki via frame plugin; push narrative to pre-visit summary Done

What follows is a structured view of the work that remains — organized by theme rather than sequence, because the order will depend on what the pilot surfaces.

Two New Subprojects

Two independent workstreams have been scoped and are ready to build. Each has its own directory alongside scp-coupler/.

Subproject · In progress

Option Box — scp-optionbox/ · port 8768

When the coupler's Plan proposes an intervention, generate a patient-held fact box: options side by side, benefits and harms in natural frequencies per 1,000 people, each harm carrying a RAC cell, evidence quality and funding stated, unknowns stated as unknowns. The same severity × probability logic the coupler already uses for ranking diagnostic possibilities now ranks intervention consequences.

  • Phase 1 — done: Schema (optionbox-schema.json), validator (validate-optionbox.js), HTML renderer with icon arrays, hand-built AF anticoagulation example (data/nnt-library/af-anticoagulation.json)
  • Phase 2: openFDA drug label + FAERS clients; RxNorm name→RxCUI lookup; on-disk cache; ONC high-priority interaction list
  • Phase 3: Test-library math — pretest p → 2×2 → per-1,000 rendering; coupler-proxy trigger route; curation queue
  • Phase 4: SCP attachment; print stylesheet; "questions to ask" footer from unknowns list
Subproject · Awaiting Epic app config

SMART on FHIR — scp-fhir/ · port 8767

Pull real clinical data from PeaceHealth's Epic system into the SCP/Coupler environment using SMART on FHIR standalone patient launch with PKCE. Epic developer account registered; app registration next. All PHI stays local; data is gitignored.

  • Phase 0 — manual: Register app at fhir.epic.com — patient-facing, standalone launch, public client (PKCE), redirect URI http://localhost:8767/callback, scopes: openid fhirUser patient/*.read. Records sandbox and production client IDs in scp-fhir/config.json (gitignored).
  • Phase 1: smart-proxy.py — PKCE flow, sandbox proof, raw bundle pull for one test patient, console summary
  • Phase 2: PeaceHealth production — swap config, Marc authenticates with MyChart credentials
  • Phase 3: Map FHIR → SCP/coupler schema: Condition → problem list, Observation → answered coupler questions, MedicationRequest → active meds, CarePlan/Goal → compare without overwriting
  • Phase 4: Dynamic client registration (refresh tokens); multi-provider merge; TEFCA IAS if needed

Key Epic quirks: aud parameter required on authorize request; Observation and CarePlan searches require category; use non-prod client ID against sandbox only; always follow Bundle next-page links.

Near-Term Work

These items are well-understood technically and follow naturally from what exists today.

Data fidelity

Populate scp-experiment with real (or realistic) SCP data

The experiment site currently uses placeholder health-log entries and visit records. Replacing these with representative data — modeled on the Superior AZ pilot — will reveal gaps in the context-fetch logic and make the Claude output meaningful enough to evaluate clinically.

  • Map all scp-field and scp-log-entry types actually used in the pilot
  • Seed scp-experiment.localhost with 2–3 representative patients
  • Confirm context fetch covers every field type relevant to the coupler
Closing the loop

Write coupler findings back to health-log

Right now, the coupler reads from the SCP but writes only to stand-alone assessment pages. The next logical step is to post a scp-log-entry item into health-log when a SOAP note is finalized — so the coupler's output becomes part of the longitudinal record it will later read.

  • Define a minimal scp-log-entry schema for a PKC-sourced entry
  • Add a "Log to health record" button (separate from "Push to Wiki")
  • Ensure logged entries carry enough metadata to distinguish them from CHW-entered data
Workflow

Multi-problem visit brief

Pre-visit summary currently operates one problem at a time. A visit typically involves several active problems. The coupler should be able to assemble a single, prioritized brief covering all problems the CHW plans to address — exported as one coherent page or section.

  • Add a "Build visit brief" button that iterates over selected problems
  • Produce a single pre-visit-summary page with all problems as sections
  • Allow CHW to deselect problems they are not addressing in this visit
Infrastructure

Person → wiki site mapping

The proxy currently hardcodes scp-experiment.localhost. For any real deployment covering more than one patient, the coupler needs to know which FedWiki site corresponds to each person_id. This mapping also needs to survive the proxy being restarted.

  • Add a simple person-to-site registry (JSON file or in-memory dict loaded at startup)
  • Push and context-fetch endpoints use the registry rather than the hardcoded constant
  • Admin endpoint or UI to register a new person ↔ site pairing

Medium-Term Work

These items depend on the near-term work being stable, or require design decisions that aren't yet settled.

Clinical quality

Problem library and prompt refinement

The coupler's value depends on the quality of the knowledge base it draws on for each problem. The current prompts are generic. A library of problem-specific frames — what findings to gather, what to watch for, what NOT YET GATHERED items are most important — would make the output actionable rather than advisory.

  • Build a problem library (JSON): problem name, key findings, red-flag items, relevant labs
  • Inject problem-specific frame into the system prompt for each Claude call
  • Allow the library to be extended by the clinical team without code changes
CHW workflow

End-to-end CHW visit flow

The current toolchain requires a technically proficient user. To be viable for the CHW pilot, the workflow must run from within the SCP page with no separate browser windows, proxy setup awareness, or JSON inspection. The experience needs to be invisible as infrastructure.

  • Test complete flow with a non-technical CHW participant
  • Document the visit steps from the CHW's point of view, not the developer's
  • Identify friction points and resolve them before the next pilot contact
  • Confirm the pre-visit summary renders correctly on mobile (CHWs often use phones)
Federation

Cross-site context fetch

In the SCP model, data lives on the patient's personal wiki site, not the CHW's. The coupler currently reads from a single known site. For real federation, it needs to read context from any authorized site in the neighborhood — following the FedWiki model of distributed, person-controlled pages.

  • Fetch context from the patient's own site (not just the experiment site)
  • Handle authorization — FedWiki "friends" security or equivalent
  • Support the case where health-log and about-me live on different sites

Longer-Term Work

These items represent larger architectural or clinical decisions that will take time to develop.

Pilot readiness

Multi-person real pilot

Moving from a single experiment patient to a real pilot cohort — even two or three participants — requires the person-mapping infrastructure, CHW workflow refinement, clinical review of prompts, and a clear plan for what constitutes a successful interaction.

Closing the evidence loop

Outcomes tracking

Did the coupler's NOT YET GATHERED items actually prompt new data collection? Did the pre-visit summary change what the CHW focused on? Answering these questions requires embedding lightweight tracking into the workflow — not surveillance, but enough to evaluate the tool's effect on care quality.

Weed's vision

Longitudinal gap analysis

The deep goal of Weed's coupler is not just to structure today's visit — it is to make cumulative gaps visible over time. A patient who has been seen twelve times without a particular finding being gathered should have that gap become progressively more prominent. This requires storing and comparing gap state across visits.

Architecture

Transition from local proxy to hosted service

The current architecture requires a Python proxy running on localhost — workable for development and small pilots, but not for deployment at scale or across sites. At some point the proxy logic needs to move to a hosted service, likely alongside the Mac Mini infrastructure already planned for SODOTO.

  • Evaluate hosting options consistent with health data sensitivity
  • Separate the Claude API key management from the application logic
  • Consider whether the proxy should be part of the FedWiki server or a standalone service

Open Questions

These are not tasks — they are questions that will shape which of the above work actually gets done and in what order.

Who reviews the clinical quality of the coupler's output?
The SOAP structure and NOT YET GATHERED items come from Claude. Without a clinician reviewing prompt design and sample outputs, there is no quality assurance on the clinical content. This is the highest-stakes open question.
What is the right relationship between the coupler and the CHW's own judgment?
The coupler should amplify the CHW's assessment, not replace it. The framing of outputs — how certain or directive they sound — matters. Weed was explicit that the tool is for the person carrying the problem, not a substitute for their agency.
How does authorization work when context crosses site boundaries?
The FedWiki security model (friends, owners, neighborhoods) is well-suited to this use case, but the coupler is currently outside that model — it fetches pages via HTTP with no authentication. Before any real patient data is involved, this needs to be resolved.
What does "done" look like for this experiment?
The experiment needs an exit criterion — a set of observations that would justify moving to a broader pilot, or a set of findings that would send the design back to the drawing board. Defining this now prevents the experiment from drifting indefinitely.
