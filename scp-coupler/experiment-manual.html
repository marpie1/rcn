1. Prerequisites

The integration requires three things to be in place before you start.

Python 3 and python-pptx

The coupler proxy is a Python 3 script. Any Python 3.8 or later will work. No additional packages are required beyond the standard library and the anthropic SDK.

FedWiki installed

FedWiki must be installed globally via npm and runnable with the wiki command. The experiment uses farm mode, which requires FedWiki 0.18 or later.

scp-experiment.localhost in /etc/hosts

The experiment site runs on a subdomain of localhost. Add this line to /etc/hosts if it is not already there:

127.0.0.1  scp-experiment.localhost

You will need administrator access (sudo) to edit that file. The line only needs to be added once.

An Anthropic API key

The coupler proxy calls Claude to generate frames and narratives. Set the key as an environment variable before starting the proxy:

export ANTHROPIC_API_KEY=sk-ant-...
The experiment site pages live at ~/.wiki/scp-experiment.localhost/pages/. If this directory is empty or missing, copy the seed pages from the production SCP wiki before proceeding.

2. Starting the System

Open two terminal windows. Run one command in each, in any order.

Terminal 1 — FedWiki

wiki --farm ~/.wiki

FedWiki starts in farm mode, serving all sites under ~/.wiki/ on port 3000. Both the production localhost site and the experiment site are served by this one process. When you see output saying the server is listening on port 3000, FedWiki is ready.

Terminal 2 — Coupler proxy

python3 ~/rcn/coupler-proxy.py

The proxy starts a ThreadingHTTPServer on port 8766. When you see Serving on http://localhost:8766, the proxy is ready. Leave both terminals open while you work — stopping either process ends that part of the system.

If port 3000 is already in use from a previous FedWiki session, stop that process first. On macOS: lsof -ti:3000 | xargs kill.

3. Opening via FedWiki

With both processes running, open the PKC landing page in the experiment wiki:

http://scp-experiment.localhost:3000/problem-knowledge-coupler

What you see

The page loads in FedWiki's standard lineup view. A FedWiki frame plugin item embeds the coupler UI at 800px height inside the page. The coupler detects the ?embed URL parameter (added automatically by the proxy when serving inside a frame) and switches to a compact layout.

Compact embed layout

In embed mode, the coupler looks different from the full-window version:

  • No page header — the FedWiki page header takes its place
  • The left sidebar is 180px wide instead of the full-size version, and the problem list is visible immediately without clicking
  • The toolbar shows a Push to Wiki button instead of the standard FedWiki button
  • The layout fits within the 800px frame height with internal scrolling
The embed layout is read from the ?embed URL parameter. If you open the coupler directly at http://localhost:8766, you get the full-window layout with the standard FedWiki button. Both layouts connect to the same proxy, the same database, and the same SCP context injection.

4. Opening the Full Window

To use the coupler outside of the FedWiki frame, open it directly in a browser tab:

http://localhost:8766

This shows the full-window layout: the standard header, the full-width sidebar with the person and problem list, and the FedWiki button in the toolbar (instead of Push to Wiki). Everything else — SCP context injection, frame generation, push to wiki, narrative, push to pre-visit-summary — works identically.

Use the full window when you want more screen space, when you are printing or exporting a frame, or when you want to view the complete SOAP view without scrolling inside a wiki frame.

5. Loading a Person and Selecting a Problem

The left sidebar shows the list of people in the local database. Click a person's name to open their record. If no people exist yet, click New Person and enter a name or identifier.

Once inside a person's record, the sidebar shows their problem list. Click a problem to open it in the main content area. If no problems exist, click Add Problem and type a short title — for example, "Uncontrolled hypertension" or "New-onset fatigue."

The problem title is the primary input to the frame generator. A clear, specific title — "Chest pain on exertion" rather than "Pain" — produces a more useful frame. The SCP context pulled from the wiki is added to the same request, so the AI sees both the title and the existing record.

The selected problem stays open when you switch between embed mode and full-window mode. Both views share the same database.

6. What the Coupler Reads from the SCP

Before generating a frame, coupler-proxy.py automatically fetches context from the experiment site. This happens every time a frame is generated — you do not need to trigger it manually.

What gets fetched

The proxy reads three pages from scp-experiment.localhost:3000:

  • health-log — vitals, symptoms, and visits recorded via SCP plugins
  • visits — visit notes and encounter summaries
  • about-me — demographic background, stated goals, chronic conditions

The content of these pages is extracted from FedWiki's JSON format, converted to plain text, and appended to the prompt sent to Claude. Claude reads this context before generating findings, so information already in the SCP pre-fills the frame rather than showing as absent.

Previewing what will be injected

To see exactly what the proxy will send to Claude before generating anything, open this URL in a browser:

http://localhost:8766/api/scp-context

The response is a human-readable HTML table showing each piece of SCP content that will be included. This is useful for verifying that the experiment site has meaningful data and that the proxy is connecting to it correctly.

If scp-experiment.localhost:3000 is not reachable, the proxy generates the frame without SCP context. The frame will still be generated; it will just start from scratch rather than from the existing record. No error is shown to the user — check the proxy terminal output for a connection warning.

7. Generating a Frame

With a problem selected, click Generate Frame. A spinner shows while the proxy fetches SCP context and sends the combined request to Claude. Frame generation takes 15–40 seconds depending on how much SCP context is available and the current API response time.

How SCP data pre-fills findings

When the frame appears, findings that correspond to data already in the SCP will show as filled or partial rather than absent. For example, if the health-log page contains a recent blood pressure reading, the OBJECTIVE finding for blood pressure will show as filled with that value, rather than showing as a gap. The AI reads the SCP entries and maps them onto the frame slots automatically.

Not all SCP data will match frame slots. The AI uses judgment about which entries are relevant to the specific problem. Entries that don't map to a slot are not shown in the frame but are visible at the /api/scp-context endpoint.

After reviewing the pre-filled frame, add any findings you know about that weren't captured in the SCP. Then run Re-Match to update the probability estimates with the complete picture.

8. Pushing the Frame to FedWiki

The button

In embed mode (inside the FedWiki frame), the toolbar shows a Push to Wiki button. In full-window mode, the same function is available via the FedWiki button in the toolbar. Both buttons do the same thing: write the current frame as a new FedWiki page on scp-experiment.localhost.

Click the button. The proxy writes the page and the coupler sends a doInternalLink postMessage to FedWiki, which opens the new page to the right in the lineup. The page title is derived from the problem title — for example, a problem titled "Uncontrolled hypertension" produces a page called pkc-uncontrolled-hypertension.

What the wiki page looks like

The page contains a paragraph item with the problem title and the date, followed by a single HTML item with five collapsible sections:

SectionContents
SUBJECTIVE Filled and partial subjective findings with their recorded values; absent findings listed as gaps
OBJECTIVE Filled and partial objective findings; absent findings listed as gaps
ASSESSMENT Ranked candidate diagnoses with probability estimates, attention codes, and supporting/refuting findings
PLAN Plan considerations with current status
NOT YET GATHERED All absent findings across all sections, collected in one place so gaps are immediately visible

Each section uses a <details><summary> element and defaults to collapsed. Click a section header to expand it. All five sections can be open at once.

Pushing the frame again for the same problem creates a new page with the current date appended to the title. It does not overwrite the previous version — both pages remain in the lineup history.

9. Narrating

The Narrate button generates a plain-language paragraph summarizing the current state of the problem record. Click it at any time after generating a frame. The proxy sends the current record to Claude and returns a paragraph covering:

  • What has been reported and measured
  • The leading diagnostic possibilities and the evidence for each
  • What remains unknown and which gaps would most change the picture if filled

The paragraph appears in the Narrate section below the frame. It is editable — click inside it to revise wording or add context before pushing it to the SCP.

Narrate is useful at the end of a visit. The paragraph is written to be understood without clinical training, so it can be shared with the person, their family, or a clinician picking up the record cold.

10. Pushing the Narrative to Pre-Visit Summary

After generating (and optionally editing) the narrative paragraph, click Push to SCP below the narrate output. This writes the paragraph to the pre-visit-summary page on scp-experiment.localhost.

What gets written

The narrative lands on the pre-visit-summary page as a collapsible HTML block. The block is labeled with the problem number, title, and date — for example:

PROBLEM 1: Uncontrolled hypertension — 2026-07-04

The block is collapsed by default. Expand it to read the full narrative paragraph. The pre-visit-summary page accumulates entries across problems and visits, so the summary page gives a complete picture of what is known across all active problems at the time of the last push.

Re-pushing

If you push a narrative for a problem that already has an entry on the pre-visit-summary page, the proxy finds the existing block by its label and replaces it in place. The page does not accumulate duplicate entries for the same problem. Only the most recent narrative for each problem is kept.

After writing, the proxy sends a doInternalLink postMessage to open the pre-visit-summary page to the right in the lineup so you can confirm what was written.

Push to SCP writes directly to the FedWiki page file on disk. The change is immediately visible to anyone viewing the page. If you push a draft narrative by accident, edit the pre-visit-summary page directly in FedWiki to correct it.

11. Viewing Results in the FedWiki Lineup

After pushing a frame or narrative, FedWiki opens the target page to the right of the current page in the lineup. This is standard FedWiki behavior — each push extends the lineup by one page.

The lineup after a typical session might look like this, left to right:

  1. problem-knowledge-coupler — the landing page with the embedded coupler
  2. pkc-uncontrolled-hypertension — the pushed frame page
  3. pre-visit-summary — the narrative summary page

All three pages are on scp-experiment.localhost. You can navigate to any of them directly at:

http://scp-experiment.localhost:3000/[page-title]

FedWiki's standard page history is available for all pushed pages — click the page flag to see the journal of changes. Each push appears as a journal entry with the timestamp of the write.

Pages pushed by the coupler proxy are written as full FedWiki page JSON files. They can be edited in FedWiki using the standard double-click-to-edit pattern, forked, or shared. They behave like any other FedWiki page.
