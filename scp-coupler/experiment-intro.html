SCP + PKC Integration — What This Experiment Tests

Two Systems, One Record

The Problem-Knowledge Coupler generates exhaustive diagnostic frames. The Shared Care Plan holds the living health record. The experiment asks: what happens when they talk to each other?

On their own, each system does one thing well. The PKC surfaces what a complete workup would ask — every finding worth gathering for a given problem, organized in SOAP order, with gaps visible. The SCP, built on FedWiki, holds what is actually known — vitals, visits, medications, diagnoses, the person's own account — accumulated over time by the person, their family, and the care team.

The gap between them is real: the PKC doesn't know what the SCP already holds, and the SCP has no mechanism for asking whether the record is complete. This experiment builds the connection between them — in both directions — on a local testbed, without touching either system's production data.

What the Experiment Does

Three integration steps were built. Each patient has their own FedWiki site (rosa-delgado.localhost:3000, alex-rivera.localhost:3000, …) and the coupler routes all wiki reads and writes to the site of the person currently selected.

Step 1 — Push frame to wiki

After generating a coupler frame, the "FedWiki" button (or "Push to Wiki" in embed mode) writes the full assessment as a FedWiki page on the selected patient's site. The page has five collapsible sections — SUBJECTIVE, OBJECTIVE, ASSESSMENT, PLAN, NOT YET GATHERED — each collapsed by default using <details><summary>. The page opens immediately to the right in the FedWiki lineup via the doInternalLink postMessage.

Step 2 — Pull SCP context into the frame

Before Claude generates a frame, coupler-proxy.py automatically fetches the health-log, visits, and about-me pages from the selected patient's wiki site and injects those entries into the record sent to the model. Claude pre-fills findings from what the SCP already knows — vitals, diagnoses, medications, and background appear in the frame rather than starting from scratch. The endpoint http://localhost:8766/api/scp-context shows a human-readable table of what will be injected before you generate anything.

Step 3 — PKC landing page in wiki

A page called problem-knowledge-coupler on a patient site embeds the coupler UI via FedWiki's frame plugin at 800px height. The coupler detects the ?embed URL parameter and switches to a compact layout: no page header, 180px sidebar with the problem list visible, and a "Push to Wiki" button in the toolbar instead of the standard "FedWiki" button. The coupler is usable without ever leaving the wiki lineup.

Narrate to Pre-Visit Summary

After generating a narrative paragraph for a problem, clicking "Push to SCP" writes the narrative to the pre-visit-summary page on the patient's site. Each narrative lands as a collapsible HTML item labeled PROBLEM N: TITLE — DATE, collapsed by default so the summary page stays scannable even as entries accumulate.

Re-pushing the narrative for a problem that already has an entry updates the existing block rather than duplicating it. The pre-visit-summary page then opens to the right in the lineup so you can confirm what was written.

What This Is Not

This is a local testbed, not a production system. The patient sites are isolated — they are not federated with WikiCafe or any other live FedWiki farm. Pages on the *.localhost patient sites do not replicate to production and are not visible outside this machine.

The experiment does not replace the standalone PKC tool. It does not replace the SCP plugins running on localhost:3000. It is one possible architecture for how these two systems could connect — built to find out what works and what doesn't before committing either system's design to it.

No clinical decisions should be made based on data from this experiment site. The SCP pages copied into the experiment are a snapshot, not a live record.

Per-Patient Wiki Sites

Each patient in the coupler's registry (scp-coupler/data/people.json) has a wiki_site field naming their own FedWiki site — e.g. rosa-delgado.localhost, alex-rivera.localhost. All sites are served by the same FedWiki farm process on port 3000, with pages stored at ~/.wiki/{site}/pages/. The coupler proxy resolves the correct site per-request from the selected person, falling back to scp-experiment.localhost if a person has no site registered.

New patient sites are provisioned automatically by sofi-proxy's /api/provision-patient, which seeds all 17 canonical page templates from ~/rcn/scp/pages/ — the standard SCP pages (health-log, visits, about-me, medications, diagnoses, my-care-team, lab-results, pre-visit-summary, and more), each with dismissible example items (all 13 plugin types support Dismiss). All pages are editable. Nothing written here touches production. Provisioning also registers the site in ~/.wiki/config.json under wikiDomains.

How to Start

Two processes need to be running. Open two terminal windows and run one command in each:

wiki --farm ~/.wiki
python3 ~/rcn/coupler-proxy.py

The first starts FedWiki in farm mode, serving localhost and all patient sites on port 3000. The second starts the coupler proxy at port 8766.

Once both are running, open a patient's SCP directly:

http://rosa-delgado.localhost:3000/view/welcome-visitors

The coupler will be embedded in the wiki lineup in compact mode. From there, all three integration steps are accessible without opening a separate browser tab.

The coupler can also be opened directly at http://localhost:8766 for the full-window experience. Both modes use the same proxy and the same database. SCP context injection happens in both modes.
Each *.localhost patient site requires a host entry in /etc/hosts. If a site doesn't load, check that 127.0.0.1 rosa-delgado.localhost (etc.) is present in that file.
